## Slices, oldest first

**Live end to end.** The Discord-style chat shell in `apps/web` runs entirely on real data (Supabase sign-in, rooms/channels/members, message history, Realtime delivery and presence) over the server-authoritative write path in `apps/api`. The AI is a real member of the chat: a goal starts an agent run (`202 + runId`), the Python `services/ai` core returns **proposals**, and Node executes them.

**A goal now produces a structured full-funnel plan**, rendered as a card: six fixed stages, per-step owners (AI / HUMAN / YOU), per-step citations, and stages left **visibly empty** where the corpus does not cover them. The owner can approve or send it back with a note, and that verdict is captured in `feedback_events` as the flywheel's first labelled data.

**Approving that plan now creates the work.** A project and one task per step, in one transaction, with the per-step owner becoming the row that the router will read. The task DAG, its state machine and its acyclicity are enforced in Postgres by trigger rather than in the runner, because the runner is the part [ADR-0001](../40-adr/0001-durable-orchestration-trigger-vs-temporal.md) already plans to replace.

**And a plan that is running can be changed without being thrown away.** Replan-by-diff was specified in Phase 0 and had nothing behind it, which became visible the moment the project panel did: a person could see fifteen steps, disagree with three, and have no move short of abandoning the project and posting a new goal, discarding every deliverable already produced. An owner now says what should change and gets a **diff** to approve, steps added, cancelled or corrected, on the same card surface and through the same authorisation boundary as the original plan. **Nothing replans on its own**, because a model proposing a change is not the same as somebody agreeing to it. Three properties are enforced in Postgres rather than in the route: a `modify` cannot touch a step's state, owner or risk tier, so an authorisation decision cannot travel through the op that looks least like one; a diff naming work that has since been approved **fails whole rather than half-applying**, because skipping the impossible ops would apply a change nobody reviewed; and a card cannot reach another room's project, which the action route could never have caught since it checks membership of the card's room and not of the project the payload names. **Cancelling a step does not release what waits on it**, which is correct rather than an oversight and is therefore said on the card, in the prompt and in a test.

**And the DAG is a graph rather than a list.** `task_deps` existed, was guarded against cycles, and held no rows for two weeks, because the planner emitted stages and steps and the only edges available would have been inferred from stage order, which states a constraint nobody made. The planner now says which steps consume which other steps' output, so the scheduler holds a step back until what it needs is approved instead of dispatching a whole plan at once. **Stage order is still presentation and nothing infers an edge from it.** The two layers disagree on purpose: the reasoning core drops a reference it cannot resolve and flattens the graph on a cycle, because a plan is worth far more than its edges and flat is what every plan used to be, while Postgres raises on the same input, because a card can also arrive from an older service or a hand edit and guessing on its behalf is how an invented edge gets in.

**The first vertical has a domain now, and it deliberately grants the AI nothing new.** The marketing module specified nine entities and the data model contained none of them, so the enforcement spine that already works (a plan step's own words raise its risk tier, the router refuses to auto-run high-risk work, Postgres refuses an illegal transition) had only prose to guard. Four tables land with their guards: campaigns and their lifecycle, room-scoped channel connections, the ad tree, and append-only campaign outcomes. **There is still no executor, no adapter call and no OAuth route**; the guards arrive before their writers on purpose, because the recorded failure here is the opposite order, with `risk_tier` unreachable for its whole life and `task_deps` holding no row for two weeks. `channel_connections` holds OAuth tokens and therefore has **no client policy and no client grant at all**, since RLS filters rows and not columns; a client is refused rather than shown nothing, and the test asserts the error. `packages/marketing` holds the spend-cap arithmetic and the ad-platform seam as pure code with no IO, with a deterministic fake as the only registered provider, so every later slice is testable without an ad account or anybody's money.

**And a deliverable can be a file.** `artifacts.storage_path` had existed for two weeks with no bucket, no policy, no reader and no writer behind it, so the panel's "this one is a file" arm was reachable only by a row nobody could create. There is a private bucket now, whose **path convention is the tenancy scheme**, a signed-URL route that reads the artifact row as the caller so RLS row visibility **is** the authorization, and a writer that removes the uploaded object if the row fails, because Postgres has no transaction across object storage. Uploads stay Node-initiated: the Python service has no storage keys by design and never handles bytes, so no proposal shape changed.

**And a person can now authorise money, which is the first thing here that spends rather than writes.** The marketing tables landed with their guards and no writer at all, so `campaigns` had a lifecycle nothing could enter. The gap was not only the writer: `create_campaign` is `high_risk`, so the router parks it at `needs_user` by design, and there was **no surface on which anybody could say yes to a campaign**. There is a campaign card now, drafted by the reasoning core for exactly the steps the router stopped for an authorisation, approved through the same boundary as a plan, and committed by `materialise_campaign` into one campaign at `ready`, which means approved and not yet sent. **Nothing publishes and no adapter is called**; the guards still arrive before their writers. **The model never proposes the budget**, and that is the load-bearing decision ([ADR-0011](../40-adr/0011-spend-cap-checked-twice.md)): once written, a figure a model invented and a figure a person authorised are the same number on the same row with the same audit trail behind it, so the owner types it and the route writes it into the card as it records the verdict. The spend cap is then **checked twice on purpose**, readably in the route and again in SQL under a row lock, because two cards approved in the same instant both pass a check made in Node and the result would be a sum of authorised caps exceeding the ceiling inside the table whose entire purpose is recording what was authorised. That duplication is the one this repository normally refuses, so both halves are pinned to the same boundary by two suites. This slice also closed a live gap of the class already recorded twice here: **`projects.budget_ceiling` had no reader and no writer anywhere**, so the spend check composed a number nothing could set and would have refused every campaign forever. And the writer shipped one defect that its own suite caught, worth recording because the shape recurs: a missing budget key made `jsonb_typeof(...) <> 'number'` evaluate to NULL rather than true, so the guard failed open and created a campaign authorising nothing while reporting itself authorised, which is the NULL twin of the `NaN` case the spend arithmetic already guards against.

**And the workspace can connect its own accounts, which is the second dead end of the same shape.** `risk.py` clamps on the words "connect", "authorise" and "credentials", so a step reading "connect your Meta ad account" is parked at `needs_user` exactly as `create_campaign` was; the campaign drafter is asked, correctly declines because an account connection is not a campaign, and the owner was told a step needed them with nowhere to go. `channel_connections` has its writer now, and **no migration came with it**: the table, its enum, its grants and its unique constraint are used exactly as they landed two slices earlier, which is what the guards-before-writers ordering is supposed to produce. The surface is the project panel rather than a card, because connections are **room-scoped on purpose** (one ad account serves every project) and because every card here is approve-or-reject where approving commits through one function, while approving a connection can commit nothing: the credential does not exist until after a redirect. **The callback lands on the web origin** ([ADR-0012](../40-adr/0012-oauth-callback-on-the-web-origin.md)), because the browser coming back carries the person's session, so the signed `state` can be bound to a user who is provably signed in; terminating at Fastify would have created the only unauthenticated mutating route in the system, holding one HMAC and writing to the one table with no RLS behind it. The state is **signed, not stored**, and what that costs (replay inside its ten-minute life, bounded by single-use codes and the table's own unique constraint) is written into the file rather than assumed away. **This is the one route group where RLS defends nothing**: the table has no grant to `authenticated` at all, so membership is checked separately by reading the room as the caller, and the projection's column list, which omits both token columns, is the entire control and is asserted directly rather than reviewed. **Only the in-repo `fake` provider is registered**, its consent screen is a page in our own app so a person can actually click Cancel, and the plaintext-token accepted risk gained its **enforced** half: `carriesRealCredentials` sits on every registry entry and the writer refuses on it, so the first person to add Meta hits a failing write instead of a paragraph they did not read.

**And a campaign a person authorised now reaches a platform, which is the first thing here that acts outside the system rather than writing to it.** `materialise_campaign` committed campaigns at `ready`, meaning authorised and not yet sent, and stopped; `ad_entities` had held its guards for a week with no writer. Approving the card **is** the publish authorisation now ([ADR-0013](../40-adr/0013-approving-a-campaign-publishes-it.md)) and the next ticker pass sends it: there is no second button, because the card already named the channel and made the owner type a cap, and a confirmation carrying no new information is one people learn to click through, which weakens every other confirmation in the product. What that cost was paid in the same commit rather than left to drift: four sentences promising "nothing is published or spent" were rewritten where they were made, including the connect callback's promise to ask before using an account, which stopped being true the moment connecting could unblock a campaign already waiting. **Postgres has no transaction across somebody else's API**, so the intent row is written _before_ the call under a key derived from the campaign id alone, and each of the four crash points resumes: the key collides and the row is read back, the campaign is selected again at `publishing`, the same key returns the same id, or the recorded `external_id` skips the adapter entirely. A record of an uncertain request is recoverable and an unrecorded certain one is not. The failure map is where the care went, because `failed` is terminal: a **policy rejection closes the campaign** and says so with the platform's own words and the fact that trying again means a new card, while a rate limit or a provider error retries unbounded at tick cadence, since a bound tripping on a transient outage would destroy a campaign somebody authorised. `checkScopes` finally has its first caller, checking permission in tool code before the call rather than learning it from a 403. **Still only the `fake` provider, no ad sets or ads** (creative does not exist yet), and **no token column is read at all**, because the fake takes no credential and handling a secret to hand to something that does not accept one is handling it for no reason. The lifecycle guard `ad_entities` shipped without lands in the same migration as its first writer, and `external_id` becomes write-once, enforced rather than commented.

**And a node exists, which is the first person in this system who is not the owner.** `escalated` means "an expert should do this", `router.ts:93` sends every human-owned step there, and twelve tasks have been sitting in that state on the live database with nowhere to go. Four marketplace tables landed with their guards a slice ago and threads landed the slice after; both landed **zero capability on purpose**. Three functions are the first writers. `user_role.human_node` had no writer since `20260724000000` and now has exactly one: `invite_node`, granted to `service_role` alone, whose only caller is a checked-in script. **Onboarding is ops-invited and that is structural rather than a policy** — there is no route, no policy and no client grant that can create a `node_profiles` row — because the recorded dead end here is a person who completes KYC and is never offered anything, and the matcher does not exist yet. So the surface tells a verified, available node that there is no work to offer and why, in the same sentence a constant holds so it can be deleted when that stops being true. The **KYC map lands inside the audit trigger it was deferred into**, five arcs and no more: nothing reaches `suspended` and nothing leaves `verified`, because neither has a writer and a map permitting an unmakeable transition is the `task_deps` defect. The trigger binds `service_role` too, so the writer cannot route around it and a node who never submitted **cannot** be verified. `decide_node_kyc`'s shape was decided by the table rather than the reverse: `node_verifications` has UPDATE revoked from `service_role` as well, so `insert ... on conflict do nothing` is the only idiom and **the verdict is derived from the rows in the table rather than from the payload**, which is what makes a replay converge instead of re-decide. Its idempotency key is per submission and not per node, deliberately inverting [ADR-0013](../40-adr/0013-approving-a-campaign-publishes-it.md): publishing twice spends money twice, where verifying twice is somebody trying again. **No real KYC provider is wired and that is now enforced** — `carriesRealPii` refuses one at the writer, the `carriesRealCredentials` pattern moved from tokens to a stranger's documents. **Credentials are claimed and never confirmed**, because confirming one needs `evidence_path`, which needs a bucket that does not exist, and a licence registry we cannot call. **Still no matcher, no offer, no engagement and no thread anybody can be admitted to**, and one correction booked rather than carried: this slice was recorded as closing `author_kind.node` and does not, since a node still cannot post anywhere.

**Retrieval is measured, not asserted.** Hybrid search (dense + sparse fused by RRF in SQL) then an in-process cross-encoder, with a threshold that drops weak chunks; **query decomposition** splits a broad goal into per-stage sub-queries, sized to how broad the goal actually is. A golden-set **eval gate runs in CI** (positive recall 1.00, coverage 1.00, zero negative leaks). When nothing clears the threshold the agent **refuses and says why** rather than inventing a plan, and decomposition is additive to grounding rather than a source of it.

**A threshold ranks; it does not decide scope, so a second gate does.** A rerank score answers "which chunk fits best", which always has an answer when the query is marketing and the corpus is marketing, so an in-vocabulary but uncovered question ("how do I set up conversion tracking in GA4") cleared the threshold by 12x over a legitimate broad goal. That is measured, not suspected, and no threshold separates the two bands. A **groundedness gate** now sits between retrieval and generation and asks whether the sources actually answer the goal. It fails closed, judges the same sources the planner will see, and distinguishes "your question is outside my sources" from "I could not check", because telling someone the first when the second happened is a false statement on a trust surface. It has its own set of in-vocabulary negatives, scored in a credentialed pass that also measures the **false-refusal** rate, since a gate judged only on what it refuses scores perfectly by refusing everything. That was not hypothetical: the first measured run refused every uncovered question **and** three goals the corpus plainly covers, so the two-sided measurement is what stopped a confident-looking 1.00 from shipping. Now 1.00 on both halves. Embeddings can run locally on **BAAI/bge-m3** ([ADR-0008](../40-adr/0008-local-bge-m3-embeddings.md)) or on OpenAI. RLS is covered by a **pgTAP suite** (22 assertions), including that an expired node sees nothing at all.

**The corpus decides which words work, which is a kind of coverage nobody thinks to measure.** "marketing plan to get **registrations**" was refused while "…**signups**" returned a full six-stage plan, against the same corpus, because the documents said one and never the other and the local threshold's margin is 1.76x. Fixed from both ends: the documents now use the words people actually use, and a curated in-code table rewrites the rest before retrieval. A dictionary or a second embedding space was the intuitive answer and is the wrong one, because dense retrieval is already the synonym layer and is not the stage that fails, and because query **expansion** is measured-fatal at a cross-encoder. Three documents closed the last uncovered funnel stage and two topics that were being refused, so measurement, partnerships and referrals now plan instead of declining. Then the crawled pages turned out to be roughly **a sixth site navigation**, trimmed away, which promptly broke a golden negative that had been passing only because junk chunks were crowding real ones out of the candidate pool. A test that passes because of garbage is not a safety property, so the leak was fixed at its source. **Corpus growth spends the threshold margin**, exactly as [ADR-0009](../40-adr/0009-local-reranker.md) warned, and three drafted negatives that leak are recorded with their scores rather than filed or deleted.

**A corpus of 17,000 words was refusing most of what it was asked, and both halves of that are now addressed.** Measured on the live database rather than estimated: seventeen documents, of which the thirteen we wrote came to **7,443 words**, some as short as 364. Every gate was working exactly as specified, so the refusals were true statements, and the dominant one was not the ranking threshold but the groundedness gate asking whether concrete steps could be written quoting only these sources, to which a 500-word principles document honestly answers no **even about its own topic**. The documents are now 1,300 to 1,900 words each, **20,946 in total**, deepened rather than widened on purpose, because every leak this project has measured came from a document written in general marketing vocabulary while a document that says more about its own subject competes only for its own topic. No titles changed, no platform is named anywhere, and the five golden negatives were probed through the real pipeline before the gate: all five still return nothing, the closest at 0.77x of the threshold. **And the eval's own green metric turned out to be the gap list.** `--gate` reports "blocked 1.00 of scope negatives" as a pass over webinar funnels, conversion tracking, app-store ranking, ad specs, influencer platforms and affiliate networks, every one of which is a reasonable thing for a founder to ask. So two things landed beside the corpus. **Every refusal is now written down** in `retrieval_gaps`, with the groundedness gate's own sentence naming what the sources lacked, which turns corpus growth from the author's intuition into a ranked queue; the write is fire-and-forget and the goal is scrubbed of identifiers first. And **a fourth core answers what the gate refuses, where refusing was the wrong product** ([ADR-0021](../40-adr/0021-a-labelled-ungrounded-tier.md)): a non-regulated marketing question that is in-domain and uncovered is answered from general practice, labelled by code rather than by the model, uncited, and structurally unable to propose a plan, so it cannot become a step that spends money. Legal, tax, permit and the regulated corners of marketing are declined in code and fall back to the refusal, and the share of ungrounded answers is a corpus-health number that should fall rather than a feature whose usage should grow.

**And what a campaign spent is now recorded, which closes the last of the four marketing tables and opens the flywheel's outcome half.** `campaign_outcomes` had carried its guards and its unique key since the domain landed, with no writer at all: the metrics sweep is that writer, riding the same ticker pass between publishing and crawling. The interesting half is that the table's own constraints decided the design rather than the other way round. It is **append-only by grant including for `service_role`**, so there is no UPDATE to fall back on and `insert ... on conflict do nothing` is the only idiom available; the unique key dedupes only windows that match **exactly**, which makes "what counts as a period" a correctness property rather than a formatting one. So a period is a **whole closed UTC day and never today**, produced by one pure function and nothing else: a partial day could never be revised into a whole one, and the next pass asking for the whole day would append an overlapping row rather than replace it, doubling the spend the optimizer reads. Days are pulled **oldest first, stopping at the first failure**, because the cursor is `max(period_end)` and writing a later day while an earlier one failed would move the cursor past it permanently. **Nothing here pauses, scales or closes anything:** a read has no terminal state, there is no campaign arc a failed measurement could take, and pausing somebody's spend because we could not read a number would be the worst available use of an uncertain measurement. Reading a campaign needs `ads:read` and deliberately not the publish scope, since a person may untick `ads:write` on a consent screen and a campaign that is already live is the worst moment for its numbers to stop. The **panel shows the figures in the same slice**, because `ProjectDetail.campaigns` was itself fetched-and-never-rendered and shipping a writer with no reader would have extended this repository's most-repeated defect rather than closed it; null renders as "No numbers yet" and never as `0`, since a zero claims a day was measured and found to have none. `20260829160000` adds the `source` check constraint the table shipped without, in the same change as its first writer: `source` is part of the unique key, so a value like `metrics` would collide with nothing and a typo would look like a label mistake while behaving like a duplicated payment record.

**And a campaign that spends past what a conversion is worth is now paused without anybody clicking, which closes the loop the last slice opened.** The metrics sweep recorded spend and deliberately stopped ("acting on a CPA ceiling needs a ceiling, which has no writer yet"); the ceiling has its writer now, and **the ceiling is the authorisation** ([ADR-0014](../40-adr/0014-cpa-ceiling-authorises-auto-pause.md)): the owner types a cost-per-conversion figure on the panel, the model never proposes it, and the next sweep pauses any live campaign whose measured whole days breach `spend > ceiling × (conversions + 1)`, an inequality chosen because it needs no division and abstains loudly on anything unmeasured, since judging an absent conversion count as zero would manufacture the worst number out of not knowing. **NULL abstains rather than blocks, deliberately inverting the budget columns**, and a ceiling of 0 is refused at contract and table both as a kill switch wearing the shape of a threshold. The crash ordering **inverts ADR-0013 and says why**: publish records intent first because the platform invents an id an unrecorded crash would lose, while a pause creates nothing and re-derives from durable rows, so the platform is called first and everything converges, where our-rows-first would open the one unacceptable window, a database claiming `paused` about a campaign still spending. The idempotency keys **carry an epoch** counting prior resume transitions, because a key derived from the campaign id alone would let a record-replay platform answer a post-resume second breach with the first pause's recorded success while the money kept moving. No failure moves a campaign anywhere (`live -> failed` is not a legal arc, pinned in pgTAP), an expired connection is announced because "your spend cannot be stopped" outranks "your numbers stopped", and **resume ships in the same slice** because an auto-pause with no way back is the dead-end shape this repository has recorded three times: owner-only, from the panel, with the warning before the click that a still-crossed ceiling re-pauses on the next check.

So `node_verifications` gets no policy and no client grant at all, refuses `permission denied` rather than zero rows **to the subject of the record**, and is append-only including for `service_role`. The rest is stated rather than glossed: **PostGIS is not enabled** and service area is a hierarchical jurisdiction code, because the matching rule the module specifies is a containment test plus a specificity ordering rather than a geometry query, and a text corpus beside a geometry node is the two-representations defect that already cost forty-seven tasks their visibility ([ADR-0015](../40-adr/0015-service-geo-is-a-jurisdiction-code.md)). **An engagement will carry no state of its own** ([ADR-0016](../40-adr/0016-an-engagement-has-no-state-of-its-own.md)): every state in its lifecycle is already a `task_state` with its arcs already enforced against `service_role`, and a second enum would drift silently, because a disagreeing engagement is a confusing screen rather than an error. **Nobody is admitted to any room**, which is load-bearing: there are no threads, so room membership would show a node the whole DAG, and the sequence puts threads before any writer that could admit anyone so the narrowing is never actually taken.

**And chat has threads now, which is the narrowing this repository recorded twice and never took.** `escalated` sends human-owned work to a marketplace that does not exist, and the reason no node can simply be admitted to the room is that room membership is coarser than the access a node should have: it would show them the entire project DAG. `room_members.scope` was the column that was supposed to fix that, and it had sat there since the second migration as unconstrained text with **no check, no policy, no helper and not one reader** for forty-four migrations. It is the fifth member of the family this repository keeps recording, and the second of the worst-shaped kind, the kind that announces itself as a control rather than as an absence, because it shipped beside `expires_at`, which _is_ enforced everywhere. It asserted 1, measured 2, and the correction is its own migration rather than an edit to the applied one. **Realtime was extended, not replaced**: both policies gained the scope conjunct in place so the time-box survives, and there are deliberately no thread topics yet, because a branch with no broadcaster and no subscriber would be a third guard with no writer in the slice whose whole subject is that anti-pattern. **And a step that needed an expert can now reach one, which closes the last live dead end in the product.** `escalated` means "an expert should do this", `router.ts:93` has sent every human-owned step there since the router landed, and the only exit was the owner taking the step on themselves. **The owner clicks "Find an expert"** and the ticker offers it to one ranked node at a time; a decline or a 48-hour expiry cascades to the next; exhaustion returns the step with a message naming it. **The dispatch is a person's click rather than a sweep**, which is the load-bearing choice: twelve tasks sit in `escalated` on the live database, and a sweep claiming them all on deploy would have pushed a dozen steps at a cold-start pool while removing the two controls that already worked. **`offers` is the first table in this domain to land with its writers** rather than ahead of them, inverting the ordering the other four followed, because `20260831120000` deferred it by name on the grounds that "its entire content is a lifecycle" and a transition map nobody can exercise is the `ad_entities` mistake. And **thread creation, booked here since the threads slice, moved to acceptance**, because slice 4 admits nobody and a thread would be a row with no reader. **And that expert can now take the work, be paid from the budget the owner authorised, and talk to them about it.** Accepting was refused by the offer lifecycle map and the button was disabled with its reason printed, because accepting is inseparable from funding escrow: `claimed → escrow_funded` is the task machine's only exit from `claimed`, so an accept that wrote no ledger row would leave somebody holding work nobody had paid for. **It is one database function.** `accept_offer` settles the offer, walks the task twice, freezes the price into an `engagements` row, models the money against `projects.budget_ceiling`, writes a balanced double-entry pair, creates the task's thread and admits the node to it, in one transaction, because written in Node it would be nine statements that can half-happen. **Nothing is charged**: the only registered payment provider is a deterministic in-repo fake, `carriesRealMoney` refuses any other before an rpc is made — the third flag of that shape after tokens and identity documents — and the counsel gate in payments-billing.md is unmoved, because modelling an obligation is not money movement. **Three obligations booked by earlier slices land with it**, all named in advance rather than discovered: the thread writer that `threads` shipped without, the counterparty pair that three migrations refused to approximate and which now joins through `engagements` (`ended_at is null` is the entire time-box, so ending the deal closes it again), and the `author_kind = 'node'` writer, answered as **their own grant on the existing client path** because a server-mediated route would be a second write path to keep in step. **Two bookings were reversed and each has an ADR.** The slice table said this slice would restore `claimed → matching`; it does not, because accept and fund are one transaction so `claimed` is transit-only and the arc has no producer ([ADR-0019](../40-adr/0019-claimed-to-matching-stays-dropped.md)), which makes **five consecutive slices that restored no arc** and says the machine was drawn wider than the product has needed. And `projects.budget_ceiling` now has **two classes of committer** rather than one, so four places compute that sum and must move in step, each pinned by a suite ([ADR-0020](../40-adr/0020-the-ceiling-has-two-committer-classes.md)). One limit is a product decision rather than a gap: `room_members` is keyed on `(room_id, user_id)`, so a node works **one step of a project at a time**, and the second acceptance is refused with a sentence rather than absorbed silently. And a hold on a step that is later cancelled would pin part of somebody's budget forever, so `held → refunded` ships with its producer: a reconcile sweep that gives the money back, ends the engagement, revokes the thread membership and says so in the room. It deliberately never touches a step that reached `done`, because that would be taking back money somebody earned.

**And the work actually gets done, reviewed and taken back if nobody does it.** `escrow_funded` had been where a funded step stops, because `escrow_funded → in_progress` had no producer: a node accepted, the owner's budget was committed, a thread existed, both people could talk in it, and nothing could happen to the work. The node **starts the step, hands it over with a note and files, and the owner approves it or sends it back**. The core loop needed **no migration at all**, which is what guards-before-writers is supposed to produce: every arc it walks was declared by `20260813120000` and walkable by nothing. **`tasks.acceptance_criteria` gets its first consumer** since it landed, as the one thing the deterministic floor check can actually check, and the check **cannot reach `approved`**: it returns the step to the node or passes it to the owner, because the AI does not decide that a person's work is finished and therefore that they are owed money. **Proof is an `artifacts` row rather than a second table** ([ADR-0022](../40-adr/0022-proof-is-an-artifact.md)), reversing a booking both entity tables carried: a second table would strand an unremovable enum value and duplicate five guard and reader surfaces, and EXIF belongs to a verdict table when an extractor exists. **A thread-scoped node still reads nothing through a policy** and slice 6 added none, so their proof comes back through a service-key projection after a caller-scoped read of their own engagement, which is the only shape the storage half permits at all. **And a step somebody took and abandoned goes back to the market** ([ADR-0023](../40-adr/0023-a-breached-deadline-reassigns.md)): the deadline is frozen onto the offer before the node accepts, they are warned once a day out, and `reassign_engagement` then unwinds the deal in **one transaction**, because a live human is one of the actors in the window and every partial state either double-commits the ceiling or takes money from somebody still working. Its task move is conditional and **raises on zero rows**, so a node who handed over in that window wins. It never touches a step already delivered, enforced in the map and in the sweep, since a deadline passing after the work arrives is the owner's failure to review. **Two arcs restored after five slices restoring none**, both with their producer in the same push, and one defect fixed with them: `cascadeRound` counted only `offered → matching`, so a reassigned task would have re-derived the round its no-show already held, collided, read back that **accepted** offer and dispatched a third node against it, which is the second objection [ADR-0019](../40-adr/0019-claimed-to-matching-stays-dropped.md) raised arriving exactly as predicted. **A thread has its own realtime topic now**, emitted beside the room's rather than instead of it, so the node stops polling and the owner keeps receiving thread messages live.

**And the expert gets paid, which is the last link in the loop and the first state anything in this system has ever reached the end of.** An owner approved an expert's work and the step stopped at `approved`: the hold still said `held` and still committed part of the budget, `held → released` was declared with nothing able to walk it, `engagements.outcome` never reached `'completed'`, and `completed_engagements` — the number slice 8 ranks and rates on — was zero on every row in the database. **Approving the work is the payout authorisation** and there is no second button, on [ADR-0013](../40-adr/0013-approving-a-campaign-publishes-it.md)'s argument and on the money flow payments-billing.md already specified: the owner authorised that exact figure when the escrow was funded at acceptance, has seen it on the step, and has just read the proof. The next ticker pass transfers and `settle_payout` settles everything else **in one transaction**, because every partial state here is a money defect somebody reconciles by hand — a released hold under a live engagement, a released hold with no ledger pair, a finished step whose hold still pins the ceiling. **Four migrations and no `task_state` migration**, which is two consecutive slices where the answer to "which migration adds the arc" is "none": `approved → payout_pending → paid → done` were all declared by `20260813120000` and walkable by nothing. The ordering **takes ADR-0013's and not ADR-0014's**, and the reason is the same one that made those two disagree: a transfer _creates_ something under an id the provider mints, so the intent is written first and each of the four crash points resumes, where a pause creates nothing and calls the platform first. **`done` gets its first producer ever, on the human arm only** — nothing here had ever reached a terminal success state, and an AI step still stopped at `approved` and was still cancellable, which was written into business-projects-workflow.md as that module's gap rather than closed from a marketplace slice. **That module has since closed it**, in the slice below. **The take rate is not deducted** ([ADR-0024](../40-adr/0024-the-take-rate-is-not-deducted-from-an-agreed-price.md)): escrow holds exactly the price the offer showed the node before they accepted, so a fee taken at release would mean every surface showed somebody a figure and then paid them a different one, and `platform_fee` lands as a column written from a constant zero until the offer can name it. One cost was **discovered by building rather than booked**: ending the deal is what pays somebody, and `engaged_counterparty` was time-boxed on `ended_at is null`, so paying an expert would have erased their name from the owner's panel at the exact moment slice 8 is about to ask the owner to rate them; the pair now survives an outcome of `completed` and only that one, because a cancelled or reassigned deal delivered nothing and there is nobody to rate. **Still nothing is transferred** — `carriesRealMoney` is now checked at two writers rather than one, it throws rather than counting so a refused pass is inert, and there is deliberately no `payout_account_id` column waiting for a Connect Express onboarding that does not exist yet.

The measuring is the interesting half, and it removed more entries than it kept. A fourth was removed by the eval rather than the fetcher. Meta's advertising standards fetched perfectly, and a 25-chunk policy hub written in general marketing vocabulary turned out to act as a magnet: it caused the retrieval gate's only leak, and on an unrelated legitimate question it took five of the top eight results while the document that actually answers that question took none. **Fetchability and usefulness are separate questions**, which is not obvious until they disagree. Two families stay uncovered and are named rather than implied: the FTC blocks our declared crawler, which we are not going to disguise, and no EU-official page was found that this fetcher can read. **Retrieval no longer depends on a paid provider at all.** Reranking moved in-process onto `bge-reranker-v2-m3` ([ADR-0009](../40-adr/0009-local-reranker.md)), matching the hosted reranker on the golden set (recall 1.00, coverage 1.00, zero leaks). That only became possible after fixing four defects in our own pipeline, which had made two standard models look unusable: decomposition emitted the maximum sub-queries on every goal, those sub-queries ran 20-30 words at a cross-encoder trained on six, one was generated every time for a funnel stage the corpus has no document for, and 40 candidates were reranked against a 43-chunk corpus where RRF already ranked the answer 1st to 3rd. **And when it goes wrong, somebody can now say so and somebody can decide.** `disputed` had been declared since the workflow domain landed, narrowed to one unusable inbound arc by a rewrite doing something else, and refused by name in every marketplace slice since — because "a `disputed` task nobody can move is the `escalated` defect on purpose", and this repository had already measured that defect at twelve stranded tasks. Slice 8 restores **all four** inbound arcs together, adds `disputed → matching`, and builds the console that makes them safe ([ADR-0026](../40-adr/0026-the-dispute-exit-map.md)). **The freeze is one statement and there is no flag:** `PAYABLE_TASK_STATES` is `('approved','payout_pending')`, so moving the step to `disputed` is what stops the money, and a flag beside the state would be a second thing the sweep has to remember to read. **Both parties can raise**, and the node's arc from `rejected` is the only act in this system a node performs against the owner — without it, an expert whose work was wrongly sent back could only redo it or stop answering, and stopping is what the no-show sweep reads as _their_ failure before reassigning the step away from them. An operator resolves it five ways, and every consequence lands in one transaction: the task arc, the escrow settlement, the engagement outcome, the thread roster, any orphaned payout, the decision and the trail. **A partial settlement is a full refund plus a new hold released inside that transaction** ([ADR-0025](../40-adr/0025-a-partial-settlement-is-a-refund-and-a-new-hold.md)), because both escrow settlements are terminal and neither reaches the other — eight ledger entries across two holds, four each, and because no second `held` row is ever visible outside the transaction, the four places that compute a project's committed budget needed no change at all. **`released` moves no money here**: it returns the step to `approved` and the existing sweep pays, reusing the recovery path built for a crash rather than opening a second way to pay somebody. `/ops` is the first ops surface and the first legitimate reader of `ledger_entries`, a table that has had RLS with no policy and no client grant since the ledger landed precisely because "the reader of raw entries is the ops console". **`profiles.role` gets its first reader in forty-six migrations**, and it is read from the database and never from the token: the JWT does not carry it, so a check against the claim would refuse everybody while looking like a working deny-by-default. A role is minted only by a script somebody runs with the secret key. **`trust_score` stops being NULL on every row**: two-sided ratings land, and the score is `avg/5` over ratings received and deliberately nothing else, because three of the four inputs the spec names cannot be computed in a build whose KYC is a fake and whose credentials can never be verified. A `disputed_resolved` deal is **readable and not rateable** — both parties keep the record, and the trust graph does not take a score from a deal an operator had to decide. **Node suspension is not built**, on this slice's own argument one table over: it would be a terminal state with no exit until a moderation console exists.

**And somebody is finally told.** Every marketplace slice from 4 to 8 closed on the same sentence, and slice 8's was the plainest: "nobody is notified of anything, still". That was not a missing convenience: `OFFER_TTL_MS` is 48 hours and `WORK_TTL_HOURS` is 168 **because** nobody is told, and `matching.ts` says so in as many words, that "anything shorter would expire against people who had not looked yet". The marketplace's deadlines were set by the absence of a doorbell. Eleven moments now derive an inbox row for the person they concern, and **the row is derived from `public.events` by a trigger rather than written beside each act** ([ADR-0028](../40-adr/0028-a-notification-is-derived-from-the-event.md)), because **six of the eleven are written by SQL functions** — `accept_offer`, `reassign_engagement`, `settle_payout`, `raise_dispute` and two guard triggers — that a helper called from `apps/api` reaches only by re-implementing their transactions in TypeScript. Deriving from the one ledger all of them already write buys the property the slice exists for: a moment cannot be recorded without the person being told, including by a writer that does not exist yet. The accepted cost is stated rather than discovered, since that trigger runs inside `settle_payout`: a defect in it aborts a payout, which is why every enrichment is a left join, the verb list is a closed `case`, and the pgTAP suite derives a row for every verb. **The dedup key lives on the notification because `events` has none**, and a replay writing the same moment twice is a thing this repository has already had to write code around. **Copy is not in the database:** the row stores the facts a sentence is made from and TypeScript composes the words, which is what makes rule 22's ban on em dashes in notification copy a unit test over every kind rather than something a reviewer has to notice in a migration. The payload is an **allow-list rather than a copy**, and that is a disclosure decision: forwarding the event's payload wholesale would have shown both parties `resolved_by`, the operator who decided their dispute. Delivery is a **third Realtime topic**, `notify:user:<uid>`, as its own policy rather than a third disjunct inside the two chat policies — what `20260906120000` refused to duplicate was the `expires_at` time-box, and a per-user topic has no membership row and no time-box to keep in step. **Only in-app is built.** Push, email and SMS each need a paid provider; preferences, digests and `delivery_log` wait for them. The 48-hour and seven-day windows are **unblocked and unchanged**, because shortening them is a decision about time zones and about what somebody asleep is entitled to, not a side effect of building a bell.

**And a step that is waiting now says what it is waiting for, which is the first thing this panel has ever said about the shape of a plan.** The DAG has had edges since `20260828120000` and no surface could mention them: a step waiting on another rendered as "Not started", the same sentence a step that is merely next in the queue gets. Measured on a live project, that was twelve of fifteen steps reading identically, in the one situation where the owner has something to do, since the way to unblock five steps is to deal with the one they all point at. `Task` carries `blockedBy` now, **resolved on the server rather than shipped as ids**: sending edges would have put a second copy of `private.task_deps_satisfied` in a React component, where it would drift silently, because a step wrongly described as blocked renders as a perfectly plausible sentence either way. **That rule had already drifted, one table over** — `DONE_STATES` claimed in its own comment to mirror the SQL and was missing `payout_pending`, so for the whole life of the payout slice a step between "the owner approved it" and "the transfer landed" was counted as unfinished on the project list while the panel beside it read "Done, payment pending" and the scheduler let its dependents run: three surfaces, two answers, nothing failing. **A cancelled dependency is a dead end, not a wait**, and reads as one, because `tasks_ready` can never clear it and the plan has to change; the variant is weight rather than the stopped badge's red, since `--red-500` measures **4.00** as text on the light panel and fails AA, which is the fifth token in this system to be chosen by eye and measured wrong, and the first to be measured before it was spent. **And the same slice gave the AI arm a terminal state**, which the payout slice had named as this module's to produce: `approved` is not terminal, "anything non-terminal may be cancelled" is a universal rule of the map, and a step that produced its artifact and passed its own check could still be cancelled by a replan and recorded in the audit trail as abandoned. `executeTask` and both owner-answer paths walk on to `done`. **No migration**, for the third consecutive slice: the arc was declared and unrestricted by `20260813120000` and simply had no walker. **The second write is conditional and a miss is a race** rather than a defect, since `approved → cancelled` is legal in exactly that window, so a lost race delivers nothing instead of announcing work that was cancelled. **`approve_work` deliberately does not finish the step**, because `PAYABLE_TASK_STATES` reads `approved` and walking it on would take the step out from under the sweep that pays the expert; the sixty-six historical `approved` rows are **not backfilled** for the same reason. Driven against the live database rather than a stub, because no route test here can fail on a select string: the exact select, the enum filter and the id scoping all answer 200, the owner sees all fifteen edges through RLS rather than zero, and the real helper on real rows produces both sentences. **Not exercised in a browser**, and the reason is recorded rather than glossed: a second API against the live database would have fired a ticker pass with no AI service reachable and escalated live tasks.

**And a question is answered on the card, which is the first time the product has asked for less than a paragraph.** Intake's questions went out as plain text and came back as one chat message the owner composed to answer all of them, which a model parsed back into slots; while the card waited it **claimed every message the owner wrote** for two hours, because that was the only way to know which message was the answer, and two cards were found holding rooms for nearly two days. The card renders now ([ADR-0029](../40-adr/0029-a-question-is-answered-on-the-card.md)): a budget band or a timeline is a row of chips, an audience or an offer is a short field with its own Save, a step the plan asked about is one field, and each answer is its own embed action through the same route every other card is acted on through. **And the agent stopped being one anonymous account, which is the first time the chat has said who is speaking.** Since `20260728120000` every AI message was `author_id = null, author_kind = 'agent'` and the client rendered all of them under one hardcoded name, so the plan, the intake questions, a delivered landing page, a campaign proposal and a notice that a campaign was paused for crossing its cost ceiling all arrived from the same account, and `events` recorded the same flat answer for each. `messages.persona` (`20260912120000`) names one of four voices, **Strategist, Content, Ads or Analyst**, chosen in `apps/api` by `personaForStage` from the step's own `tasks.stage`, a column the planner already fills. **A persona is a voice and never a writer** ([ADR-0031](../40-adr/0031-an-agent-persona-is-a-voice-not-a-writer.md)), which was the whole risk in the request that started this: the shape most multi-agent products take is several agents that each plan and each spend, and this system's guardrails all assume the opposite, since three campaigns of 400 pass a 1000 ceiling individually and commit 1200 between them. So nothing about who may act moved. One writer to the task DAG, one `routeTask`, one `checkSpendCap`, one `apply_plan_diff`, and no model chooses the label. **`text` with two named checks rather than an enum**, on ADR-0022's argument that an enum value cannot be dropped and this set is expected to move in both directions: `messages_persona_known` closes the set and `messages_persona_agent_only` refuses a persona on a system notice or, worse, on a person's message wearing an AI's name. **The insert policy gained one conjunct and had to be retyped whole**, because `alter policy ... with check` replaces the expression rather than appending to it, and a conjunct dropped in the retyping would read as the chat quietly breaking rather than as a security change; choosing a specialist for a message written before specialists existed would put a guess into the record a person reads to reconstruct what happened. **`services/ai` is untouched** and all five prompts still open "You are Octopus", because a persona changes attribution rather than wording, so there was no prompt change and no eval to gate. **The control run is what makes the suite worth having**: run without the migration, 7 of its 10 assertions fail and the 3 that pass are precisely the regression ones, which is the difference between a suite that tests the change and a suite that tests its own fixtures. The live run found nothing wrong and proved the two halves that no test in this repository can reach: a goal posted through the real stack produced a `strategist`-signed started notice where a muted system line used to be, then a `strategist`-signed plan card, while a `persona` forged into the POST body came back null.

**And the four voices joined the members panel, where the only honest thing to show turned out to be a step title.** The panel listed people and nothing else, so a room with a step running looked exactly like an idle one and the AI existed only as messages after the fact. `ProjectSummary.working` now carries the stage and title of every task the executor is holding, computed by the same pure summariser the progress counts come from and riding the project list the client **already** refetches on every message, because the things that change it all announce themselves in the room. That is the whole mechanism: no polling, no second subscription, no server-side agent presence table, and the panel moves when something actually happened. **`WORKING_STATES` is two states rather than one**, since the critic reading a draft is still the agent busy on that step from the reader's side and stopping at `ai_running` would blink the panel off between the draft and its review; `routing` is excluded because the scheduler is still deciding who takes it and no voice owns it yet. **The wire carries the stage rather than the persona**, so the client maps it through the same registry it renders names out of and there is no second copy of `personaForStage` to go stale the first time a stage moves between voices. **The pulse is the second use of the one reserved glow** and means what it has always meant, with the activity line carrying the same state in words so nothing rests on colour or motion. **A separate `UiPersona` rather than a widened `UiMember`**, because a persona has no user id, never goes offline and never expires, and widening the member type would have forced four literals elsewhere to carry fields that mean nothing for a person. **The Strategist's busy state is the one thing here that is a claim rather than a reading**, and it is marked as such: planning happens before a project exists, so the longest wait in the product has no row to be found, and this browser sets the flag when its own run is accepted and clears it on a Strategist message, a system notice, or after three minutes. The timeout is not a fallback for a bug. A run can end in ways this client never sees, so a pulse with no way to stop would be a lie that outlives the thing it described; a tab backgrounded through a whole run still pulses until it expires, which is written down rather than solved by matching on text. The live run found nothing wrong and showed the thing working on real rows: Content on "Build landing page copy around message match" and the Analyst on "Measure email by clicks and revenue, not opens", both with `animation-name: breathe` and the glow shadow in computed style while the two idle voices stayed a plain green dot, and the project panel's step lines reading "Content" and "Ads" where they had read "Octopus".

**And you can now address one of the four by name, which is the first time a sentence in the chat has been aimed at part of the system rather than at all of it.** The idea this came from was nine bots that each plan and each act, and that is the shape the whole slice was built to refuse: this system's guardrails all assume one writer, and three campaigns of 400 pass a 1000 ceiling individually while committing 1200 between them. So `@Ads move the budget to Meta` does not move a budget. `startRun` parses the mention **before anything else it does**, resolves the project running in that room, posts one acknowledgement in the voice addressed, and calls the same `produceDiff` an owner's own request from the project panel takes; the owner approves the card or does not, and `apply_plan_diff` behind that card is still the only thing that changes a running DAG. **The branch runs first for two reasons that are easy to get wrong.** A new goal closes the intake cards that were sharpening the previous one, and a mention is not a new goal, so closing them would throw away questions somebody is part-way through; and sending "@Ads" to the classifier would spend a call to learn nothing. **`@Strategist` routes the same way**, deliberately: a fresh intake on a running project produces a plan competing with the one already executing, which is exactly the regeneration replan-by-diff exists to prevent, so the Strategist answers by diff like everybody else and skips the line it would otherwise be saying to itself. **A member's mention is still an ordinary goal**, because the cards are about the owner's own business and a member's sentence is not an authorisation. **The grammar had to live in `packages/contracts`** rather than in core, because two independent readers must agree on it: the composer decides what to highlight and offer in the browser, and `startRun` decides what to route in Fastify, and a second regex would have disagreed at exactly the cases nobody tests, `someone@ads.com` and `@Adsy` among them. `@Octopus` is not a mention: it addresses the whole thing, which is what every message already does. **Enter completes the mention rather than sending**, which is the one failure the composer must not have. **`agent-runner.ts` got its first test file in its life**, which is worth saying rather than quietly fixing: it is the only path by which anything the reasoning core says becomes visible, and every test it had came from route suites that mock it out entirely. The eleven cases are as much about what does not happen as what does, and one of them was mutation-checked by breaking the persona argument and watching exactly the two discriminating assertions fail. The live run found nothing wrong and produced the more interesting half by accident: the reasoning core read the request, found sources that did not cover it, and declined to propose anything, so the room got an `ads`-signed sentence saying the plan is unchanged and why, rather than a card. **And the card that asks for money had been rendering as a column of single words, which nobody had looked at.** `.stage` is a three-column grid because a plan card numbers its stages 01, 02, 03 down the left, and the campaign and replan cards reuse that wrapper for one unnumbered body: the body was therefore laid into the **22px number column**, and every line wrapped to a single word down the left edge of the card. Both had been live for as long as the card has existed, on the two questions a person is actually answering when they read it: what is this, and how well is it backed.

**And the reasoning core stopped being the product, which is the largest thing this repository has decided against itself.** Everything had been loaded onto our own core: a hand-written corpus, an in-process embedder and cross-encoder at 4.6 GB of weights and an 8 GB deployment floor, a planning turn measured at 121 s end to end on a 16-thread box, one pinned OpenAI key for generation, and a fourth flywheel mechanism ending in a proprietary fine-tune. The owner's decision is that the first MVP works the way Cursor works: the harness is the product and the model is a pluggable connector, with the workspace bringing its own key. [ADR-0032](../40-adr/0032-reasoning-providers-are-workspace-connectors.md) records it, and this slice is only the record: no table, no route, no dialect, and no Current shape section moves, because nothing exists to describe. **Two things were assessed before the decision rather than after it, and either could have made it wrong.** The first is that the harness is already provider-agnostic, as a fact about the code rather than a hope: `routeTask`, the twice-checked spend cap, the plan card as the authorisation boundary, `materialise_plan`, the marketplace SQL functions, thread RLS and the event-derived notifications do not read which model wrote the proposal they are checking, so a connector changes **who proposes** and never **who acts**, and [ADR-0006](../40-adr/0006-python-ai-service-node-backend.md) holds unmodified. The second is that "learn from other models' answers", which is the obvious thing to want next, is only safe as data: OpenAI, Anthropic and Google each forbid using their output to build a competing model, read on 2026-09-04, and two arguments would hold even if they did not, since there is no proprietary generator here for a distillation set to be a set for, and a model's prose ingested into the corpus becomes a **citation**, which is the precise failure the retrieval stack exists to prevent. So **a provider's output is a lead, never a source**, and mechanism 4 in `learning-flywheel.md` is narrowed to human corrections and measured outcomes on our own data. **The temptation this decision spends most of its words refusing is the one every vendor now ships.** Provider-native tools invite an agent that publishes, spends and connects from inside the model call, which in this system would be a side effect that passed no `routeTask`, no spend cap and no card, so they are admissible only where they are read-only or artifact-producing, and image generation is therefore a proposal Node executes rather than a tool the model runs. **The classification split is the decision most likely to be quietly undone later**, so it is written with its cost attached: decomposition, the groundedness gate and intake stay on the house model because they are pinned at temperature 0 and their thresholds were measured there, which means that on a workspace using its own key the goal sentence, the intake answers and the retrieved sources block still reach the house provider, and the trigger to revisit is the first customer whose data-processing agreement forbids it. **Supabase Vault was rejected rather than overlooked**, which is worth recording because it is the obvious answer: Vault decrypts inside Postgres for any role that can read `vault.decrypted_secrets` and `services/ai` holds `service_role`, so storing model keys there would hand the Python container every customer's key and defeat the one property the encryption exists to buy. And **Octopus as an MCP connector inside ChatGPT or Claude was rejected outright**, which is the cheap version of "works with any model" and gives away the thing being built: behind somebody else's client the spend cap and the plan card stop being guarantees and become tools a foreign agent loop calls. One drift was found on the way and fixed rather than noted: `tech-stack.md` pinned an `openai` Python SDK in `services/ai`, which has never been a dependency, since `providers.py` has used plain `httpx` since it was written and says so in its own module docstring.

**And the Python half learned to answer on somebody else's model, which is the smallest piece of that decision and the one everything after it rests on.** A `GenerationTarget` now arrives on the request, carrying a vendor, a registry id, a model and the customer's key, and `services/ai` stores none of it. With no target every call is byte-for-byte what it was, which matters more than it sounds: a workspace that connects nothing is the majority case and the one nobody would be watching, so that is the regression that would have shipped in silence, and there is a test that reconstructs the exact old request body to catch it. Four dialects, plain `httpx`, no vendor SDK: OpenAI-compatible, Anthropic, Google's Interactions API, and a deterministic fake that never opens a socket.

**Two of the vendor facts behind those dialects are the kind that fail invisibly, which is why they were verified against the reference rather than recalled.** Claude models released after Opus 4.6 reject every `temperature` but 1.0 with a 400, so the Anthropic dialect sends none at all: the house path's 0 for JSON and 0.3 for prose would each have failed every call on precisely the two strong models a workspace is most likely to connect. And Gemini has an OpenAI-compatibility layer that would have made this a one-line change, which is exactly why it is not used: it is beta and **silently ignores parameters it does not support**, so a token cap or a JSON request looks applied when it is not. That is the same defect this file already records once, when `complete_json` omitted `temperature` and inherited the API default of 1.0, and five runs of one unchanged commit returned coverage 0.97 to 1.00 because the sub-queries resampled every time. A parameter that is quietly dropped and a parameter that was never sent produce the same passing response.

**The third fact is a budget rather than a parameter, and it has a precedent in this repository.** Anthropic requires `max_tokens` and adaptive thinking spends it, so a 4000-token plan budget would go on thinking and the JSON would arrive truncated. That is `generation_max_tokens_long` all over again: at 900 tokens every whole-funnel goal came back as cited prose, nothing errored, nothing was logged as broken, and the product's marquee feature was quietly off. So the dialect adds 4000 tokens of headroom on top of whatever the caller asked for, and a `stop_reason` of `max_tokens` is raised as a `ProviderError` rather than returned as text, because `ProviderError` is what makes the planner's corrective retry and then its prose fallback run.

**Neither Anthropic nor Google has OpenAI's cheap `json_object`, so JSON is asked for as an instruction and unwrapped afterwards.** Schema mode exists on both and is deliberately not built: it needs a schema per caller, each vendor restricts what the schema may contain, and the callers all validate with pydantic regardless, which is the check that actually holds. What the instruction path needs instead is tolerance for a model complying imperfectly, so `_extract_json_object` strips a code fence and takes the first `{` to the last `}`. Throwing a usable plan away over a fence would turn compliance into a refusal. The trigger to build schema mode is written down: a `card_rate` below 1.0 on either vendor.

**Which calls may take a target is a safety boundary, not a routing detail, and it is now asserted rather than described.** Plan, its retry, its prose fallback, execute, campaign draft, replan and the ungrounded tier all run on the workspace's model. Query decomposition, the groundedness gate and intake never do, and a test pins each of the three receiving `None`, because they are pinned at temperature 0 and their thresholds were measured on the house model, the gate two-sided by `--gate`. Routing those to whatever a workspace happened to connect would move a safety threshold by configuration and invalidate the only measurement standing behind it. Retrieval is untouched altogether: embedding and rerank are in-process, so no corpus text leaves the process because somebody picked a different reasoning model.

**`PlanResponse` now reports who answered rather than who was asked.** The planner sets `provider` and `model` on every response it builds, including the prose fallback, and the ungrounded tier on its own; a refusal that generated nothing leaves both null, since there is no model to name. The distinction is what lets Node throw when it sent a target and got back no attribution: an older service ignoring the target would otherwise misroute a customer's work to the house key and look identical from the outside.

**The 422 body was a real leak and not a precaution.** Pydantic v2 reports a missing field against the parent and puts the whole parent **object** in `input`, so FastAPI's default handler returns the customer's API key in a validation error, from a path nobody thinks of as a data path. Verified directly against pydantic 2.13 before the handler was written, and both cases are in the suite: the missing field, which leaks, and the wrong enum value, which does not, so nobody concludes from the harmless one that the handler is unnecessary. The key is a `SecretStr` unwrapped only where the outbound header is built, and it reaches no log line, no `what=` string and no exception message.

**A fake vendor exists so the seam can be walked without spending anything.** One canned JSON object that validates simultaneously as a six-stage plan, a written artifact, a campaign decline and a replan diff, which works only because it names no `kind` of its own: a literal value would satisfy one of the four models and turn the other three into refusals, which on the live stack reads as a broken seam rather than a wrong fixture. Its prose says what it is, in the room, so a fake answer cannot be mistaken for a cheap one.

**Verified, and what is still owed.** 592 tests green and ruff clean. The OpenAI model ids were re-listed against the account, confirming `gpt-5.4`, `gpt-5.4-mini` and `gpt-5.4-nano` and leaving the house default where it is. On a running service: `/health` reports `openai` and `gpt-5.4`; a real goal ("my CPA on facebook ads keeps climbing") with an `openai_compatible` target returned `grounded-plan-v1`, six of six stages, 13 citations, `provider: openai`, `model: gpt-5.4`; the same goal on the fake vendor returned a six-stage card titled "Fake plan from the fake vendor" attributed to `fake / fake-strong` with no socket opened, which is the seam walk the vendor exists for; and a `generation` missing its `model` came back as a 422 carrying the field name and not the canary key. **Not yet run: the live Anthropic and Google calls and the `--plan` admission numbers for either**, because those need the owner's own keys, which are deliberately not in the repository. `--plan --provider anthropic --model claude-sonnet-5 --key-env ANTHROPIC_API_KEY` and the Google equivalent are the gate a registry entry has to pass, deferred to the slice that adds the connect-time key check, and their `card_rate` and `clean_rate` belong in this log before either vendor is offered to anybody.

**Nothing in this slice sends a target.** No Node change, no migration, no settings surface, so every call in the running system is still the house key. That is the point of cutting it here: the seam can be wrong in one language at a time.

**And a workspace can now hand over its own key, which is the half of the connector decision that touches money and therefore the half worth building slowly.** Two tables landed together and they take opposite postures, which makes this the clearest worked pair in the schema of the rule that RLS filters rows and not columns. `model_connections` holds a customer's paid API key and has **no client policy and no client grant at all**, so a client asking for it is refused with `42501` rather than shown zero rows, and the owner of the very room is refused too, which is what proves the refusal is not a policy somebody could widen later. `model_routes` says that the Ads voice runs on GPT-5.4, which is the same fact every message chip in the room will show next to the message that voice wrote, so members read it under a policy and nobody writes it as a client.

**The key arrives encrypted in the same change that creates its table, which is `channel_connections`' accepted risk finally being met on a different table.** That risk named its own trigger, "the first real provider credential, in that change and not after it, because the interval between a real token landing and the encryption landing is exactly the exposure". This was that trigger and there was no interval. AES-256-GCM over plain `node:crypto`, with the additional authenticated data bound to the row, so a ciphertext copied out of one room's row and into another's fails to open rather than decrypting under the wrong owner. `envelope.test.ts` asserts the failures rather than the round trip, because a round trip would still pass if the tag were ignored or the AAD dropped: a tampered ciphertext, a tampered tag, a **truncated** tag, a swapped IV, the wrong master key and each of the three wrong AADs all throw, with one identical message so nothing tells an attacker which half of a guess was right.

**Supabase Vault would have been less code and was rejected for a reason specific to this system.** Vault decrypts inside Postgres for any role that can read `vault.decrypted_secrets`, and `services/ai` holds `service_role`, so keys there would be readable by the Python container with a select. The property being bought is that decryption is confined to the Node code that builds the outbound request, and `openSecretForProvider` is named so that "where does decryption happen" has an answer somebody can grep for. The compose file now sets `MODEL_KEY_SECRET: ''` on the AI container, which is the only line in that file that is a security control rather than a tuning knob: the service takes `apps/api/.env` wholesale through `env_file`, and `environment` beats `env_file`.

**A key is checked with the provider before it is stored, and that is why connecting is a route rather than a field.** `verifyKey` calls the vendor's own list-models endpoint, which is the one request all three answer for free: it authenticates, needs no model id, and bills nothing. A refused key is a 400 and an unreachable provider is a 502, and **nothing is written on either path**. Without it a mistyped key would fail four minutes into an agent run, in a system notice, on a surface where a person cannot tell a typo from an outage.

**Revoking a key also deletes the routes that pointed at it**, which is the piece with no precedent in the channel group. A route naming a provider whose key is gone would be a role that resolves to nothing, and the resolver would then have to choose between failing the run and silently using the house key. Neither is a good answer, so the state is made unreachable rather than handled: those roles fall back to Auto, which the surface already has to explain anyway.

**The registry is a checked-in file and the code never branches on a model id.** Providers, their dialects and their model lists live in `packages/contracts` with `carriesRealCredentials` reading exactly as it does in `packages/marketing` and `packages/payments`, and every lookup raises on an unregistered name rather than answering false, because "a provider we have never heard of certainly does not carry real credentials" is the inversion that matters. Ids are data: `labelForModel` renders one it does not recognise as itself, since an unknown id is still the true answer to what wrote a thing.

Every projection the Node code selects was then run against the real schema, because route tests stub the PostgREST client and a wrong column name can only fail at runtime.

The API log contains neither the OpenAI key, nor the master key, nor the fake key. The fixtures were then deleted from the owner's workspace; the events stayed, because they are the record of what was actually done.

**What is not built, and is deliberately not.** Nothing consumes a route. No agent run resolves one into a target, so every call still goes to the house key, and there is no surface: the four routes are reachable by curl and by four typed functions in `api-client.ts` that nothing calls. `Message.model` is in the contract and is always null, because the column does not exist yet and no message in this system was written by a model anybody chose. Key rotation is named with the first rotation as its trigger. The seam was cut here so that the credential can be wrong on its own, before anything depends on it being right.

**And now a workspace's own choice actually decides who proposes, which is the slice that turns two tables into a product.** `resolveGeneration` reads the room's route for a role, opens the sealed key through the one decrypting function, and puts a target on the request; `toWire` renames it onto the body. The roles are not a new vocabulary, they are facts Node already had: the plan is the Strategist's, an executed step takes `personaForStage(tasks.stage)` so a landing page is written by Content on Content's model, a campaign card is `ads` by name because the router parks a step for spend authorisation whatever stage it was filed under, and a replan diff takes the voice that signs it, so `@Ads move the budget to Meta` comes back signed by Ads **and written on the model routed to Ads**. Splitting those two would have made the signature decorative. `/plan` sends two targets because it has two exits: the grounded card is the Strategist's and a gate refusal takes the labelled ungrounded tier, which is its own role a workspace can point somewhere else, and the service reports whichever one actually ran.

**A room that has routed nothing sends no `generation` field at all**, rather than `generation: null`, and a test asserts that rather than a comment claiming it. That is what makes "nothing changed for everybody else" something a diff can settle.

**The attribution column is the opposite of the persona column one migration back, on purpose.** `persona` closed its set with a check, on the argument that a client trusts the four names it renders. Model ids belong to vendors, who retire and rename them without asking, so `messages.model` is `text` with a length bound and nothing else: a closed set would mean the day a vendor ships a model this repository has not listed, a run that succeeded and produced real work fails at the write, and the person loses the output to a label. What the table can refuse is a model on a system notice or a person's message. What it cannot refuse, and what `apps/api` therefore has to hold, is the other half of the rule: **only text a model actually wrote carries one.** Every run notice, sweep notice, waiting digest and question card is an `agent` row composed in TypeScript, and each of those writes `model: null` explicitly rather than leaving it to the column default, so the claim is in the code somebody greps. Intake is the case worth stating: a model did classify the goal, and the words are still ours.

**`messages_insert_own` gained `and model is null`, which meant retyping the whole predicate again.** `alter policy ... with check` replaces the expression rather than appending to it, so `message_persona.sql` (10) and `thread_scope.sql` (55) were both re-run against the restatement inside the same rolled-back transaction, and both passed. That is not ceremony: a conjunct dropped in a retyping fails nothing until somebody asserts the capability it protected, and every such failure reads as "the chat stopped working" rather than as a security change.

**`task_runs` takes the pair per attempt, and the second reader is why the column exists at all.** The executor stamps its own delivery from the response it just received, which needs no column. The heal sweep re-delivers an artifact some earlier process wrote, possibly days later and possibly after the owner changed their routes, so it reads `task_runs.model` back through `artifacts.task_run_id` rather than asking the routes what would answer today, which would stamp a message with a model that never saw it.

**Failing loud was chosen over falling back, twice.** A route with no `MODEL_KEY_SECRET` on the server, and a ciphertext that will not open, both stop the run with a system notice naming the variable. The tempting behaviour is to shrug and use the house key, and it is wrong in two directions at once: the workspace chose a provider and would be silently billed to us instead, and the message would be stamped with a model the owner did not pick. A route pointing at a provider with no live connection is a different case and warns rather than stopping, because revoking a key deletes its routes, so that state is stale bookkeeping rather than a decision anybody is making now.

**Verified against the live stack, and that is where the two real defects were.** The first: slice 1 set `provider` and `model` in the planner alone, so `/execute`, `/campaign` and `/replan` came back grounded and unattributed. The second was that check itself: written as "a routed call must name a model", it would have turned a correct refusal into a failed run on every routed room, because a refusal calls no provider and honestly names none. With the routes still set and the master key removed from the container, the run failed with `MODEL_KEY_SECRET` named in the room and nothing written. **Not built here.** Nothing renders the model yet: the chip beside the Agent badge, the thumbs on a reply and the Models block itself are the web slice. `retrieval_gaps` does not carry the pair, so the fallback tier is routed and not yet measured per provider. The `creative` role has a picker value and no producer.

**Then the admission gate was run against Claude Sonnet 5, and it failed in a way that was entirely our fault.** `--plan` scored `card_rate` below 1.0 with cases reading `FELL BACK to prose (no card)`, and the owner noticed something the score did not say: money had been spent and nothing had come back. Three defects, none of them the model's.

**The first was a 60-second HTTP timeout in `services/ai`**, sized when every generation went to the house OpenAI key, which answers in seconds and does no thinking. A connected reasoning model does not: on a 16-chunk sources block Sonnet 5 spends thousands of tokens thinking before it writes the first character of the plan, and the reply runs past a minute.

**The second turned that into a bill.** `_post_with_retry` treated the read timeout as transient and tried three times. A read timeout means the provider accepted the request and is generating, so the completion is produced and billed whatever we do next, and each retry bought another full one for the same reason the first had "failed" — three abandoned plans per case, all paid for, all discarded. Read, write and pool timeouts are now terminal. Connect failures still retry, because nothing was generated and another attempt costs nothing.

**The third was arithmetic.** The Anthropic dialect added 4000 tokens of headroom for thinking, giving an 8000-token cap. Measured across five runs of one prompt, thinking came in at 3217, 3246, 3445, 3528 and then **7191** tokens: adaptive, with a long tail. At 7191 the cap left 809 tokens for a plan that needs about 2500, so the JSON arrived cut off, `ProviderError` fired, the corrective retry ran, and the turn fell to prose. The headroom is 12000 now, which covers the worst observed run with margin and costs nothing when it is not reached, since providers bill tokens produced rather than tokens allowed.

**Node's budget moved with it, and the ordering is now the stated invariant.** `AI_REQUEST_TIMEOUT_MS` defaulted to 90s, below the AI service's new 240s per-call ceiling, which would have meant Node hanging up on Python mid-answer and reporting a healthy service as unresponsive — the exact failure the 30s-to-90s change had been made to fix. It is 300s, and the rule is that the outer budget only ever fires when the inner one has already failed to. The accepted cost is that a genuinely hung service takes five minutes to report instead of ninety seconds, which is a longer wait on a rare fault against every connector plan failing on a common one. The paragraph in `architecture.md` arguing the opposite was rewritten rather than deleted, because the argument was right for the house path and is worth being able to find.

**Verified on the exact case that failed:** three runs of the 16-chunk `cpa-too-high` prompt, three valid cards, thinking 4679, 5342 and 7111 tokens. The third used 10,525 output tokens in total and would have truncated under the old cap.

**The measurement that started this is void.** No `card_rate` for Anthropic is recorded here, because what was measured was a 60-second timeout and an 8000-token ceiling, not Claude Sonnet 5. The gate still has to be run, and the numbers still belong in this log before either vendor is offered to anybody. **This is the second time a competent model has been scored badly through this repository's own harness**, so the rule is written where the dialect is documented rather than left in a commit message: audit the caller before the model.

### An ungrounded answer says who gave it, and the owner can say whether it helped (ADR-0032, slice 4 of seven)

**The "another model answers when Octopus cannot" half, built as data rather than as a feature.** Slice 3 routed the fallback tier to whichever connector a workspace named for it. Nothing recorded which one answered, and nothing could say whether the answer was any good, so the tier that most depends on the model was the only one nobody could measure. Two migrations, a parameter in Python and one route in Node close that.

**`retrieval_gaps` gains `provider` and `model`, and the default is the design.** `gaps.py` takes them as parameters defaulting to `None` rather than reading the configured model, because **the common row in that table is a refusal and a refusal calls no model at all**: `refusing-v0` never reached generation, and both gate cores are the gate declining or being unavailable. Filling them in from settings would put an attribution on sentences no model wrote, which is the mistake `messages_model_agent_only` exists to make impossible one table over, and it would be wrong in the other direction too, since a workspace's Fallback route need not be the house model. Only `ungrounded-general-v1` carries the pair, and it is handed the `PlanResponse` the tier produced, so the row names what **answered** rather than what was asked for.

**Why the columns are worth a migration at all.** Once a workspace routes Fallback to its own connector, two rows with the identical core, the identical gate `reason` and the identical near misses can be two entirely different products, and reading the queue without the pair is reading an average of things that did not happen. That is also the whole of what they are for. A queue naming the model behind each gap is exactly the shape a distillation set has, and it is explicitly not one: nothing ingests these rows, nothing trains on them, house provider or connector alike. A provider's output is a lead, never a source.

**`feedback_events` gains its second subject.** Every path into it since `20260812130000` went through a card, because at the time every AI output a person could judge was one. The labelled ungrounded tier is not: it answers in prose, carries no card by construction, and rests on the model rather than on the corpus. `message_id` joins `embed_id` as a nullable sibling, and `helpful` / `not_helpful` join the two card verdicts in the same column. The wording is asymmetric on purpose: a card asks for an authorisation and consequences follow both its verdicts, while a prose answer asks for nothing and nothing downstream materialises from these two.

**No cross-column check requiring exactly one subject**, and the reason is a race rather than a preference. Both columns are `on delete set null`, so a room cascade deleting its messages and its embeds would turn an ordinary cleanup into a constraint violation depending on which cascade Postgres ran first. The write path sets exactly one; the table declines to make a deletion order into a failure. `set null` rather than `cascade` for the same family of reason: `subject` holds what was actually judged at decision time, so a label outlives its subject and stays readable evidence.

**A defect the route's own test suite found, which is worth recording because it looks like nothing.** The 409 for "this message carries a card" was first written against `message.embed`, the rendered value. `toEmbed` deliberately returns `null` for a payload it cannot parse, so a corrupt row degrades to a plain message rather than breaking the stream, which is right for rendering and wrong for a refusal: a message whose card failed to parse would then take a **second** verdict, and one output would be counted twice. Presence is a fact about the join; parseability is a fact about the payload. The route now asks the raw column, and a test with a deliberately unparseable payload pins it.

**Three refusals, each protecting the rate from a different kind of nonsense**: a message no model wrote (`model` null, so a run notice, a sweep notice or a waiting digest would be a label on a sentence composed in TypeScript), a person's or a node's message, and a message carrying a card. The message is read as the caller with the pinned `MESSAGE_COLUMNS`, so RLS decides what exists and an invisible message is 404 rather than 403; ownership is a separate question answered by `resolveRoom` with 403. The insert is service-role, because a label is the server's record of a decision it saw.

**Verified against the live compose stack, and the honest limitation is stated first.** No Anthropic or Google key was available in this session, so the connector half ran on the built-in `fake` vendor, which exists for exactly this and spends nothing. The Anthropic and Google wire shapes are pinned by `MockTransport` in slice 1 and were driven live in slice 3; what this run exercised is the routing, the ledger, the attribution invariant and the label route, none of which is vendor-specific.

**What the live run showed, in order, including the runs that did not do what the plan expected.** The scope negative named in the plan, "how do I build a webinar funnel for my course", came back `refusing-v0` twice: nothing cleared the 0.0013 rerank threshold, so the domain check refused before the gate ever ran and the tier never fired. Both rows landed with `provider` and `model` null, which is the assertion for a refusal and was got for free. **The groundedness gate is a model call and is not deterministic**, which showed up next: a goal that scored `unsupported` on a direct probe came back sufficient through the full run and produced a grounded plan on the house model. A goal further from coverage while still in-vocabulary, exact SPF and DKIM records for a lifecycle email, reached the tier reliably. That run left four consecutive messages in the room, and the four together are the whole invariant in one query: the ungrounded answer stamped `fake-strong` with no card, the run notice above it null, the grounded plan stamped `gpt-5.4` with a card, and its notice null. The gap row read `ungrounded-general-v1 / fake / fake-strong` with the gate's own sentence naming what was missing.

**The regulated case was the one most worth driving, and it behaved.** A GDPR cookie-consent question cleared the domain check with 8 chunks, the gate judged the corpus did not cover it, and `is_regulated` declined the tier **before any provider was called**, so the row came back `refusing-ungrounded-v1` naming nobody. A customer's own key is never spent on a question this tier refuses to answer, and that is now demonstrated rather than argued.

**The label route was driven through every path**: the owner rating the ungrounded answer 201 with the note trimmed by the contract and `subject` carrying the body, model and persona; a room member who is not the owner 403; a run notice 409 with "only an answer a model wrote can be rated"; the plan card 409 with "Rate the card instead."; a message in no visible room 404; a card verdict word sent to the prose route 400. Rating the same message again returned 201 and left **two** rows, which is what append-only means here: the table has no client `UPDATE`, so a changed mind is a second row and the latest wins. The per-provider join then ran against real rows and returned one model with one `helpful` and one `not_helpful` against it.

**The migration-version drift fired again**, as it has on every slice applied through the MCP without exception: both were stamped from the wall clock as `2026090412…` and corrected in a separate call, after which the audit in `supabase/README.md` reported 98 files against 98 recorded. Advisors show no new lint beyond `feedback_events_message_idx` reporting `unused_index`, which is what a new index looks like on the day it lands; the new foreign key is not reported unindexed, so the partial index covers it.

**Not built here.** The control itself: nothing in `apps/web` calls `labelMessage`, and the thumbs, the model chip and the Models block are all the web slice. Vendor web search on the fallback call. The `creative` role still has a picker value and no producer. And the `service_role` `UPDATE` grant on `feedback_events` remains the known gap `20260812130000` opened, recorded rather than quietly inherited.

### The Cursor-shaped surface: a workspace picks its models in the rail, and every reply says which one wrote it (ADR-0032, slice 5 of seven)

**Four slices of connector plumbing had no surface, and this is it.** A key could be connected, checked, sealed and revoked; a route could be set; every proposal ran on it and every message carried the model that answered. All of it was reachable only through curl. This slice is the Models block in the room rail, the model chip on a message head, the "Runs on" line under each of the four voices, and the Helpful / Not helpful control on the one answer that has no card.

**The block went in the rail because that argument was already settled, on a different table.** `ConnectedAccounts` was first built into the project panel, which was structurally defensible and failed on the only test that matters: that panel is a modal called "The work" and the first person to look for account settings could not find it. A model connection is the same kind of fact as an ad account, room-scoped and set once and read often, so it took the same home and, deliberately, the same classes. The connection rows, the text-button actions, the quiet detail lines and the error sentence are the neighbour's, because a second visual language for "a thing this workspace has connected" would be a difference that means nothing. Five new classes were needed and no new tokens.

**Four rules carry the block, and each one is a lie the surface could otherwise tell.** The key is not renderable, because `ModelSettingsResponse` has no field for one, so a projection that started returning credentials fails to typecheck in the browser rather than reaching it; what is shown is the last four characters. **Auto names itself**, as "Auto (house default: GPT-5.4)" read from the AI service's own `/health`, and falls back to "Auto (house default)" when the service did not answer instead of guessing a model, because that option's whole job is to report which model will actually answer. **A role is editable only when there is something to choose**, so Creative on a workspace that has connected only a text provider renders a sentence rather than a select with one dead option. And **Creative admits it is not read yet**, since image generation is slice 6 and a picker that quietly did nothing would be worse than one that says so.

**Owner-only controls are absent for a member, never disabled.** A member sees which providers are connected and reads the six routes as text lines, because which model answers is a fact about the replies they are already reading; they see no Disconnect link, no connect form and no select. Verified by signing in as a real second member of the room rather than by reading the JSX: zero buttons and zero selects inside the block, and the routes rendered as prose.

**The copy went into TypeScript for the reason `notification-copy.ts` did.** Rule 22 bans em dashes in product copy and this is the surface where somebody pastes a paid credential, so every sentence lives in `lib/models-copy.ts` and a suite walks all of them. The assertions that turned out to be worth writing are not the dash ones: the storage line must say what happens to the key ("Stored encrypted. Used only to call this provider for this workspace.") and must **not** say "secure" or "never shared", because those are reassurances rather than facts, and this file is the one place a later edit would be tempted to add one.

**Two reads became one, and that was a correctness choice rather than a saving.** The Models block and the "Runs on" line under each voice read the same settings, so `ChatApp` holds them and passes them down. Two fetches of one endpoint would let the two halves of a single panel disagree for as long as the second request took to land. The read is deliberately **not** refetched on every message, unlike the project list: nothing an agent does changes a route, only a person on this surface does, and they say so by calling back.

**A duplication the browser found immediately.** Each option first read "Fake (testing) > Fake (testing) · Fake strong": the optgroup already names the provider, so repeating it inside every option was noise in a 288px column. The option is now the model's name alone. Found by dumping the rendered `<option>` list rather than by looking at a screenshot, which is the habit worth keeping for a control whose text is generated.

**The thumbs render in exactly one place on a real room, and that is the point.** Across 33 rendered messages the control appeared once, under the ungrounded fallback answer, while five model-written plan and campaign messages carried a chip and no control and every notice, digest and recorded goal carried neither. That single query is the whole invariant: a card already has a verdict, a message no model wrote has nobody to judge, and the tier that answers in prose with no citations is the one output whose quality rests on the model.

**Verified live on the compose stack with the built-in `fake` vendor**, no key of any vendor's spent. A wrong key was refused with "That key was refused by the provider.", the field kept its value and nothing was written; a valid one connected and the row read "Connected" with its hint; routing Strategist changed its rail line to "Runs on Fake strong" within one round trip while the other three stayed on GPT-5.4; the choice survived a reload; and Disconnect took the route with it, leaving all four voices back on the house default and the ciphertext columns null. Contrast was measured **through the browser**, compositing each colour on the surface it actually sits on rather than parsing a declaration: the model chip is 4.82 light and 6.08 dark, the "Runs on" line 4.99 and 5.70, the "saved" marker 4.61, the detail lines 7.27 and 6.62. 77 web tests green across six files, typecheck and Prettier clean.

**Two limitations found rather than assumed, and both are named in the module doc.** The room rail is hidden below 1080px by a media query that predates all of this, so the Models block is desktop-only and a phone cannot connect a model; that is the whole rail's behaviour and changing it is not this slice's business. And a label does not survive a reload, since nothing fetches it back, so the buttons reappear and a second verdict appends. The table is append-only and the latest wins, so that is the storage doing what it says rather than a bug, but it is stated on the surface's own doc rather than left for somebody to discover.

**One defect found in passing and left alone, deliberately** (rule 20). Every load of `/app` throws React error #418, a hydration mismatch, because `formatTime` in `apps/web/lib/adapt.ts` formats with the local clock: the container renders 13:24 and the browser renders 17:24 for the same row. It predates this slice, it is a real bug on a page this slice did not otherwise touch, and folding a timezone fix into the connector surface would have made both harder to review. Recorded here and raised as its own task.

### The first thing this system produces that is not a sentence (ADR-0033, slice 6 of seven)

**Every deliverable Octopus had ever made was text.** `artifacts.storage_path` has existed since
`20260813160000`, the private bucket and its tenancy policy since `20260829124000`, and
`writeFileArtifact` since the proof slice, with exactly one caller: a human node uploading
evidence that they finished a step. The AI arm wrote prose. A creative step came back as a brief
whose first sentence said, in as many words, that **this system cannot generate images yet**.

That sentence was true until [ADR-0032](../40-adr/0032-reasoning-providers-are-workspace-connectors.md)
stopped making it true. A workspace can connect its own Google key and route the `creative` role
at an image model, and for one slice that route was a preference nothing read. This slice reads it.

**The seam did not move to accommodate bytes, and that was the first decision.** `services/ai`
emits a sixth proposal kind, `generate_image`, carrying a prompt, a count of one to three and one
of four aspect ratios; `apps/api` performs it. Returning base64 from the Python service was the
obvious alternative and it is wrong three times over: that process holds no storage key by design,
so the bytes would have had nowhere to go except back across an HTTP hop built to carry sentences;
a live customer credential would reach a second process with no use for it; and a proposal
executed by the side that is allowed to act is the shape of every other act in this system.
`ExecuteRequest.creative` is the mirror image: `provider`, `model` and `images`, deliberately
**without** an `api_key`, because deciding whether to ask for a picture needs no credential.

**The brief is the deliverable and the images ride with it.** It carries the citations, it is the
record of what was asked for, and it is what a person hands to a designer when the generated image
is wrong. So every failure path ends in the same place: the step reaches `done`, the brief lands,
and one sentence in the same message says what happened. Five of them, one per `ImageGenError`
kind, because a refused key is a key to re-paste and a rate limit is a wait and telling somebody
"the provider returned 429" is telling them a number. On the same message rather than a second
one: a delivery and the reason it is thinner than expected are one event, and two rows would
notify twice.

**The prompt is built in code from the brief's own Concept and Art direction sections.** Asking
the model for its own image prompt beside the brief would have created a second deliverable that
nothing renders and nobody reads, and the first time the two disagreed the picture would have come
from the one that was never on the card. Shot list is excluded because three frames folded into
one prompt asks for a single picture of three ideas, and Specs because a ratio is a field the
vendor validates rather than prose to parse.

**The subtle half is that the brief's opening sentence became conditional.** `instruction_for` now
has two openings and one body, and the capability is **withheld** from the reasoning core rather
than ignored on the way back when the deployment flag is off or the routed model cannot draw.
Told it could be drawn and then drawing nothing, the product would have written a false statement
into the deliverable itself, which is worse than an absent feature. The corollary is that a
workspace with no Creative route gets **no second message** about it: the brief already says so,
in the deliverable, and a room message repeating it would be noise on every creative step of every
workspace that has connected nothing, addressed largely to members who could not connect one.

`20260914120000` adds `artifacts.content_type`: nullable, no backfill, no default, constrained to
rows that actually have a file. Its reader is a browser deciding whether it is being handed a
picture, and the only other source for that decision is a filename `safeFilename` sanitised out of
a title a model wrote. `artifacts.sql` grew from 15 assertions to 18, dry-run inside a transaction
with the DDL (18 of 18) and controlled without it (15 of 18, the three new ones failing `42703` on
the missing column). No new advisor lint.

**The card counts the images and never shows one.** A signed URL is a ten-minute bearer credential
and an `action_embeds` row is stored and re-broadcast on every room update, so a link in the
payload would be a credential written to a table and handed to the room for as long as the row
lives; and the stream re-renders on every broadcast, so an inline `<img>` would mint one per
artifact per re-render for everybody with the room open. The card says "3 images, in the project
panel." and the panel mints one link when one person clicks to see one.

**A retry must not draw twice**, which is the failure that would cost real money. The executor is
not durable, so a crash between the images and the delivery leaves the step to the heal sweep, and
a second run would otherwise spend the customer's quota again on pictures they already have. The
existing `asset` rows on the task are the idempotency key, exactly as the artifact id is the
delivery message's. That path is covered by a test rather than driven live: reaching it needs a
worker killed inside a window of two adjacent writes.

**Verified on the compose stack with the built-in `fake` vendor**, so the whole path was walked
without spending a vendor's quota: connect, route Creative at `fake-image`, execute, upload,
render. A brief step produced its brief on the house model and **three `asset` rows**, each with
`content_type = 'image/png'` under `<project_id>/<artifact_id>/image-N.png`; both signed URLs
fetched returned `200 image/png` and 70 bytes, which is the fake vendor's 1×1 PNG, so the type Node
uploaded with is the type Storage serves. The card rendered "3 images, in the project panel.", the
embed payload carried three `{artifactId, contentType}` pairs, a `projectId` and **no string
containing `http`**, and the panel rendered all three from `img.work-artifact-image` after three
separate clicks. Contrast on `.artifact-files` measured through the browser by compositing on a
canvas: **4.99 light, 5.70 dark**, both above the 4.5 floor for 12px text. No horizontal overflow
at 375px.

**The flag was verified by turning it off, not by reading it.** With `IMAGE_GEN_ENABLED=false` a
second brief step produced its brief and **zero** assets, the brief did not promise images, the
card carried no files, and no failure sentence was appended, because no attempt was made. That is
the withheld-capability decision working: the deployment's answer reached the prompt rather than
only the executor.

**Driving the stack found a defect the tests could not.** Every generated image rendered its own
"No sources are cited for this, so treat it as unverified." line, three in a row under three
pictures. Not false: a generated image carries no citations by design, because copying the brief's
labels onto it would present it as sourced when it is not. But rule 10 exists so an uncited
**claim** cannot pass as grounded, and a picture makes no claim the corpus could have supported,
while the brief it came from sits directly above with its own sources. Three repeats of a warning
that means nothing here is how a reader learns to skip the sentence where it means something. The
warning is now suppressed for an image artifact and kept for every text artifact and every
non-image file, through one shared `isImageArtifact` so the panel and the card read the same rule.

**Two things about the verification are worth being straight about.** The brief step was **seeded
by SQL** rather than produced by a plan card: the corpus's plans for the goals in that workspace
contain copy steps and no brief step, and a replan diff is model-generated, so neither could be
relied on to produce one. `materialise_plan` is untouched and covered by its own 42 pgTAP
assertions. And the image failure sentences were exercised by test rather than live, because
making a real vendor refuse mid-run is not something a verification can arrange honestly.

### The first live image call, and the three things it found (ADR-0033, slice 6 follow-up)

The workspace owner connected a real Google AI Studio key and routed Creative at
`gemini-3.1-flash-image`. Everything in the slice above had been walked with the
in-repo fake vendor, which returns a constant PNG **before any fetch**, so the
entire Gemini request shape had never executed once. Three live runs, each one
finding something the tests could not.

**The connect check is visible and it is not a generation.** Google's usage
dashboard showed one API request and, under Generate content, "No data
available": `verifyKey` calls `GET /v1beta/models` before storing, which is the
whole point of checking a key on the settings surface rather than four minutes
into an agent run.

**Run one: a 400 that said nothing.** The step delivered its brief and reported
"The image provider declined to draw this brief." That sentence was wrong and the
code had no way to know: `statusError` mapped 400 to `policy` on the argument
that our request shape is pinned by a test, so the field a vendor rejects must be
the prompt. **The test pins our side of the wire and says nothing about the
vendor's.** Worse, the response body was discarded, so the log line carried a
number and no explanation. An error nobody can diagnose is the failure shape rule
16 exists to prevent, and it took a live call to notice because every stubbed
test agreed with itself.

**Run two, after keeping the body: the actual answer.** `The value 'image/png' is
not supported for 'response_format.mime_type'. Supported values: 'image/jpeg'.`
The format was chosen from documentation, with a comment arguing that ad creative
somebody may put type over should not be a re-compressed JPEG. The argument is
sound and the API does not offer the choice. One constant now serves the request,
the stored `content_type` and the object's extension, because a row that
describes bytes it does not hold is exactly what that column exists to prevent.
An ambiguous 400 now reads as **ours** rather than as a verdict on somebody's
creative, and a safety refusal is read off the vendor's own words instead of
guessed from a status code.

**Run three: the request was accepted and the account was not.** 429, `Quota
exceeded for metric: generate_content_free_tier_input_token_count, **limit: 0**,
model: gemini-3.1-flash-image`. Not an allowance spent: an allowance of none.
Image generation on that model needs billing enabled on the Google project, which
is the owner's decision and not something a verification can arrange.

**What is proven and what is not, stated separately.** Proven live against a real
vendor: the route resolves, the sealed key opens, the request is built and sent,
the body reaches validation, and every failure ends with the step at `done`, the
brief delivered with its citations, and a true sentence in the room. Three
different vendor failures produced three different correct sentences. Still
unproven: that a **successful** response parses into bytes, uploads and renders,
because no successful response has ever been received. The success path has been
exercised end to end only through the fake vendor, whose bytes are real and whose
wire is not. That gap closes with one billed image call the day billing is on.

### The first real picture, and the two guesses between it and us (ADR-0033)

Billing was enabled on the workspace's Google project, which is what the free
tier's `limit: 0` had been asking for, and the run that followed produced this
system's first generated image: **1024x1024, 543 KB, `image/jpeg`**, stored as an
`asset` artifact under `<project>/<artifact>/image-1.jpg`, delivered beside its
brief, counted on the card as "1 image, in the project panel." and rendered in
the panel at 320px on one click of one signed URL. The picture is on brief: the
Content voice wrote a concept about testing genuinely different hooks rather than
micro-tweaking, and that is what the frame shows.

**It took two more calls to get there and both were the same mistake.** The call
came back 200 with 858 output tokens, and the reader said "no image data". It
knew two paths: `output_image.data`, which the documentation names, and a walk of
`steps[].content[]`, which is the response's own structure and what the text path
already does. The bytes were under neither, nested in a step's content block
under a key this code did not have, in a body that also carries `usage`,
`service_tier`, per-step signatures and several token-count breakdowns.

Guessing one more key would have been the **third** guess in a row, after
`image/png` and after reading a 400 as a policy refusal. So the reader stopped
looking for a path and started looking for the value: the shallowest string under
a payload-shaped key that is long enough to be a picture. What this code needs is
not a path, it is the image, and the vendor does not promise a nesting. Two
guards keep it honest, because the same response carries a 140-character
`signature` and a looser rule would have uploaded that as a JPEG.

**The diagnostic that found it is worth more than the fix.** A 200 whose image
cannot be located is the hardest failure to read from a log, and the body is
megabytes of base64, so the error now carries the response's **shape** with every
string replaced by its length. One log line, one read, one fix.

**And one measurement error worth recording, because it nearly became a defect
report.** The image was measured at 2x2 pixels for a 1024x1024 source and that
looked exactly like a flex sizing bug, complete with a plausible explanation
about `max-width: 100%` against an indefinite container. It was the modal's entry
animation: measured again once it settled, 320x320 inside a 643px column, capped
by the rule that was written for it. The screenshot is what corrected it. Measure
after the thing has finished moving.

### The picture was not in the chat, and the reason it was not was wrong (ADR-0033)

The card printed "1 image, in the project panel." and the owner asked why the
picture was not in the chat. The recorded reason was that the message stream
re-renders on every broadcast, so an inline image would mint a signed URL per
artifact **per re-render** for everybody with the room open, and a signed URL is
a ten-minute bearer credential.

**That is not how React works.** Messages are keyed by `m.id`, so a broadcast
re-renders the list without re-mounting an existing card, and an effect keyed on
the artifact runs once per mount. The claim was reasoned wrong, presented as a
security argument, and written into an ADR decision and three module docs, where
it sat until somebody generated a real image and asked an obvious question.

The real cost is smaller and specific: opening a room with many delivered images
would mint many credentials at once, for every viewer, without anybody asking for
them. That is an argument against fetching **eagerly**, not against rendering.
So the card renders the images and each one fetches its link only when its card
is on screen, through an `IntersectionObserver` that disconnects on first fire.
One fetch per card per session, however much the list re-renders.

The argument that settled it is the one the card was built on. An approved step
used to write its work into a table only SQL could reach, which read as the
product having stopped, and that is why this card exists at all. A picture
somebody has to go and find in a panel is the same defect one size smaller.

**Verified with a wrinkle worth writing down.** In the preview pane the observer
never fired and the images stayed blank, which looked exactly like a broken
effect. `IntersectionObserver` callbacks run as part of the rendering steps, and
the pane was **hidden**, so the page was not rendering at all. Taking a
screenshot forced a paint, the observer fired, and precisely one image loaded:
the one on screen. The three off-screen holders stayed empty, which is the lazy
behaviour proving itself by accident. A hidden page loading no images is correct
behaviour, and a verification that cannot tell that apart from a bug is a
verification worth distrusting.
