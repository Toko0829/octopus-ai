## Slices, oldest first

**Live end to end.** The Discord-style chat shell in `apps/web` runs entirely on real data (Supabase sign-in, rooms/channels/members, message history, Realtime delivery and presence) over the server-authoritative write path in `apps/api`. The AI is a real member of the chat: a goal starts an agent run (`202 + runId`), the Python `services/ai` core returns **proposals**, and Node executes them.

**A goal now produces a structured full-funnel plan**, rendered as a card: six fixed stages, per-step owners (AI / HUMAN / YOU), per-step citations, and stages left **visibly empty** where the corpus does not cover them. The owner can approve or send it back with a note, and that verdict is captured in `feedback_events` as the flywheel's first labelled data.

**Approving that plan now creates the work.** A project and one task per step, in one transaction, with the per-step owner becoming the row that the router will read. The task DAG, its state machine and its acyclicity are enforced in Postgres by trigger rather than in the runner, because the runner is the part [ADR-0001](../40-adr/0001-durable-orchestration-trigger-vs-temporal.md) already plans to replace.

**And a plan that is running can be changed without being thrown away.** Replan-by-diff was specified in Phase 0 and had nothing behind it, which became visible the moment the project panel did: a person could see fifteen steps, disagree with three, and have no move short of abandoning the project and posting a new goal, discarding every deliverable already produced. An owner now says what should change and gets a **diff** to approve, steps added, cancelled or corrected, on the same card surface and through the same authorisation boundary as the original plan. **Nothing replans on its own**, because a model proposing a change is not the same as somebody agreeing to it. Three properties are enforced in Postgres rather than in the route: a `modify` cannot touch a step's state, owner or risk tier, so an authorisation decision cannot travel through the op that looks least like one; a diff naming work that has since been approved **fails whole rather than half-applying**, because skipping the impossible ops would apply a change nobody reviewed; and a card cannot reach another room's project, which the action route could never have caught since it checks membership of the card's room and not of the project the payload names. **Cancelling a step does not release what waits on it**, which is correct rather than an oversight and is therefore said on the card, in the prompt and in a test.

**And the DAG is a graph rather than a list.** `task_deps` existed, was guarded against cycles, and held no rows for two weeks, because the planner emitted stages and steps and the only edges available would have been inferred from stage order, which states a constraint nobody made. The planner now says which steps consume which other steps' output, so the scheduler holds a step back until what it needs is approved instead of dispatching a whole plan at once. **Stage order is still presentation and nothing infers an edge from it.** The two layers disagree on purpose: the reasoning core drops a reference it cannot resolve and flattens the graph on a cycle, because a plan is worth far more than its edges and flat is what every plan used to be, while Postgres raises on the same input, because a card can also arrive from an older service or a hand edit and guessing on its behalf is how an invented edge gets in.

**The first vertical has a domain now, and it deliberately grants the AI nothing new.** The marketing module specified nine entities and the data model contained none of them, so the enforcement spine that already works (a plan step's own words raise its risk tier, the router refuses to auto-run high-risk work, Postgres refuses an illegal transition) had only prose to guard. Four tables land with their guards: campaigns and their lifecycle, room-scoped channel connections, the ad tree, and append-only campaign outcomes. **There is still no executor, no adapter call and no OAuth route**; the guards arrive before their writers on purpose, because the recorded failure here is the opposite order, with `risk_tier` unreachable for its whole life and `task_deps` holding no row for two weeks. `channel_connections` holds OAuth tokens and therefore has **no client policy and no client grant at all**, since RLS filters rows and not columns; a client is refused rather than shown nothing, and the test asserts the error. `packages/marketing` holds the spend-cap arithmetic and the ad-platform seam as pure code with no IO, with a deterministic fake as the only registered provider, so every later slice is testable without an ad account or anybody's money.

**And a deliverable can be a file.** `artifacts.storage_path` had existed for two weeks with no bucket, no policy, no reader and no writer behind it, so the panel's "this one is a file" arm was reachable only by a row nobody could create. There is a private bucket now, whose **path convention is the tenancy scheme**, a signed-URL route that reads the artifact row as the caller so RLS row visibility **is** the authorization, and a writer that removes the uploaded object if the row fails, because Postgres has no transaction across object storage. Uploads stay Node-initiated: the Python service has no storage keys by design and never handles bytes, so no proposal shape changed.

**And a person can now authorise money, which is the first thing here that spends rather than writes.** The marketing tables landed with their guards and no writer at all, so `campaigns` had a lifecycle nothing could enter. The gap was not only the writer: `create_campaign` is `high_risk`, so the router parks it at `needs_user` by design, and there was **no surface on which anybody could say yes to a campaign**. There is a campaign card now, drafted by the reasoning core for exactly the steps the router stopped for an authorisation, approved through the same boundary as a plan, and committed by `materialise_campaign` into one campaign at `ready`, which means approved and not yet sent. **Nothing publishes and no adapter is called**; the guards still arrive before their writers. **The model never proposes the budget**, and that is the load-bearing decision ([ADR-0011](../40-adr/0011-spend-cap-checked-twice.md)): once written, a figure a model invented and a figure a person authorised are the same number on the same row with the same audit trail behind it, so the owner types it and the route writes it into the card as it records the verdict. The spend cap is then **checked twice on purpose**, readably in the route and again in SQL under a row lock, because two cards approved in the same instant both pass a check made in Node and the result would be a sum of authorised caps exceeding the ceiling inside the table whose entire purpose is recording what was authorised. That duplication is the one this repository normally refuses, so both halves are pinned to the same boundary by two suites. This slice also closed a live gap of the class already recorded twice here: **`projects.budget_ceiling` had no reader and no writer anywhere**, so the spend check composed a number nothing could set and would have refused every campaign forever. And the writer shipped one defect that its own suite caught, worth recording because the shape recurs: a missing budget key made `jsonb_typeof(...) <> 'number'` evaluate to NULL rather than true, so the guard failed open and created a campaign authorising nothing while reporting itself authorised, which is the NULL twin of the `NaN` case the spend arithmetic already guards against.

**And the workspace can connect its own accounts, which is the second dead end of the same shape.** `risk.py` clamps on the words "connect", "authorise" and "credentials", so a step reading "connect your Meta ad account" is parked at `needs_user` exactly as `create_campaign` was; the campaign drafter is asked, correctly declines because an account connection is not a campaign, and the owner was told a step needed them with nowhere to go. `channel_connections` has its writer now, and **no migration came with it**: the table, its enum, its grants and its unique constraint are used exactly as they landed two slices earlier, which is what the guards-before-writers ordering is supposed to produce. The surface is the project panel rather than a card, because connections are **room-scoped on purpose** (one ad account serves every project) and because every card here is approve-or-reject where approving commits through one function, while approving a connection can commit nothing: the credential does not exist until after a redirect. **The callback lands on the web origin** ([ADR-0012](../40-adr/0012-oauth-callback-on-the-web-origin.md)), because the browser coming back carries the person's session, so the signed `state` can be bound to a user who is provably signed in; terminating at Fastify would have created the only unauthenticated mutating route in the system, holding one HMAC and writing to the one table with no RLS behind it. The state is **signed, not stored**, and what that costs (replay inside its ten-minute life, bounded by single-use codes and the table's own unique constraint) is written into the file rather than assumed away. **This is the one route group where RLS defends nothing**: the table has no grant to `authenticated` at all, so membership is checked separately by reading the room as the caller, and the projection's column list, which omits both token columns, is the entire control and is asserted directly rather than reviewed. **Only the in-repo `fake` provider is registered**, its consent screen is a page in our own app so a person can actually click Cancel, and the plaintext-token accepted risk gained its **enforced** half: `carriesRealCredentials` sits on every registry entry and the writer refuses on it, so the first person to add Meta hits a failing write instead of a paragraph they did not read.

**And a campaign a person authorised now reaches a platform, which is the first thing here that acts outside the system rather than writing to it.** `materialise_campaign` committed campaigns at `ready`, meaning authorised and not yet sent, and stopped; `ad_entities` had held its guards for a week with no writer. Approving the card **is** the publish authorisation now ([ADR-0013](../40-adr/0013-approving-a-campaign-publishes-it.md)) and the next ticker pass sends it: there is no second button, because the card already named the channel and made the owner type a cap, and a confirmation carrying no new information is one people learn to click through, which weakens every other confirmation in the product. What that cost was paid in the same commit rather than left to drift: four sentences promising "nothing is published or spent" were rewritten where they were made, including the connect callback's promise to ask before using an account, which stopped being true the moment connecting could unblock a campaign already waiting. **Postgres has no transaction across somebody else's API**, so the intent row is written _before_ the call under a key derived from the campaign id alone, and each of the four crash points resumes: the key collides and the row is read back, the campaign is selected again at `publishing`, the same key returns the same id, or the recorded `external_id` skips the adapter entirely. A record of an uncertain request is recoverable and an unrecorded certain one is not. The failure map is where the care went, because `failed` is terminal: a **policy rejection closes the campaign** and says so with the platform's own words and the fact that trying again means a new card, while a rate limit or a provider error retries unbounded at tick cadence, since a bound tripping on a transient outage would destroy a campaign somebody authorised. `checkScopes` finally has its first caller, checking permission in tool code before the call rather than learning it from a 403. **Still only the `fake` provider, no ad sets or ads** (creative does not exist yet), and **no token column is read at all**, because the fake takes no credential and handling a secret to hand to something that does not accept one is handling it for no reason. The lifecycle guard `ad_entities` shipped without lands in the same migration as its first writer, and `external_id` becomes write-once, enforced rather than commented.

**And a node exists, which is the first person in this system who is not the owner.** `escalated` means "an expert should do this", `router.ts:93` sends every human-owned step there, and twelve tasks have been sitting in that state on the live database with nowhere to go. Four marketplace tables landed with their guards a slice ago and threads landed the slice after; both landed **zero capability on purpose**. Three functions are the first writers. `user_role.human_node` had no writer since `20260724000000` and now has exactly one: `invite_node`, granted to `service_role` alone, whose only caller is a checked-in script. **Onboarding is ops-invited and that is structural rather than a policy** — there is no route, no policy and no client grant that can create a `node_profiles` row — because the recorded dead end here is a person who completes KYC and is never offered anything, and the matcher does not exist yet. So the surface tells a verified, available node that there is no work to offer and why, in the same sentence a constant holds so it can be deleted when that stops being true. The **KYC map lands inside the audit trigger it was deferred into**, five arcs and no more: nothing reaches `suspended` and nothing leaves `verified`, because neither has a writer and a map permitting an unmakeable transition is the `task_deps` defect. The trigger binds `service_role` too, so the writer cannot route around it and a node who never submitted **cannot** be verified. `decide_node_kyc`'s shape was decided by the table rather than the reverse: `node_verifications` has UPDATE revoked from `service_role` as well, so `insert ... on conflict do nothing` is the only idiom and **the verdict is derived from the rows in the table rather than from the payload**, which is what makes a replay converge instead of re-decide. Its idempotency key is per submission and not per node, deliberately inverting [ADR-0013](../40-adr/0013-approving-a-campaign-publishes-it.md): publishing twice spends money twice, where verifying twice is somebody trying again. **No real KYC provider is wired and that is now enforced** — `carriesRealPii` refuses one at the writer, the `carriesRealCredentials` pattern moved from tokens to a stranger's documents. **Credentials are claimed and never confirmed**, because confirming one needs `evidence_path`, which needs a bucket that does not exist, and a licence registry we cannot call. **Still no matcher, no offer, no engagement and no thread anybody can be admitted to**, and one correction booked rather than carried: this slice was recorded as closing `author_kind.node` and does not, since a node still cannot post anywhere.

**Retrieval is measured, not asserted.** Hybrid search (dense + sparse fused by RRF in SQL) then an in-process cross-encoder, with a threshold that drops weak chunks; **query decomposition** splits a broad goal into per-stage sub-queries, sized to how broad the goal actually is. A golden-set **eval gate runs in CI** (positive recall 1.00, coverage 1.00, zero negative leaks). When nothing clears the threshold the agent **refuses and says why** rather than inventing a plan, and decomposition is additive to grounding rather than a source of it.

**A threshold ranks; it does not decide scope, so a second gate does.** A rerank score answers "which chunk fits best", which always has an answer when the query is marketing and the corpus is marketing, so an in-vocabulary but uncovered question ("how do I set up conversion tracking in GA4") cleared the threshold by 12x over a legitimate broad goal. That is measured, not suspected, and no threshold separates the two bands. A **groundedness gate** now sits between retrieval and generation and asks whether the sources actually answer the goal. It fails closed, judges the same sources the planner will see, and distinguishes "your question is outside my sources" from "I could not check", because telling someone the first when the second happened is a false statement on a trust surface. It has its own set of in-vocabulary negatives, scored in a credentialed pass that also measures the **false-refusal** rate, since a gate judged only on what it refuses scores perfectly by refusing everything. That was not hypothetical: the first measured run refused every uncovered question **and** three goals the corpus plainly covers, so the two-sided measurement is what stopped a confident-looking 1.00 from shipping. Now 1.00 on both halves. Embeddings can run locally on **BAAI/bge-m3** ([ADR-0008](../40-adr/0008-local-bge-m3-embeddings.md)) or on OpenAI. RLS is covered by a **pgTAP suite** (22 assertions), including that an expired node sees nothing at all.

**The corpus decides which words work, which is a kind of coverage nobody thinks to measure.** "marketing plan to get **registrations**" was refused while "…**signups**" returned a full six-stage plan, against the same corpus, because the documents said one and never the other and the local threshold's margin is 1.76x. Fixed from both ends: the documents now use the words people actually use, and a curated in-code table rewrites the rest before retrieval. A dictionary or a second embedding space was the intuitive answer and is the wrong one, because dense retrieval is already the synonym layer and is not the stage that fails, and because query **expansion** is measured-fatal at a cross-encoder. Three documents closed the last uncovered funnel stage and two topics that were being refused, so measurement, partnerships and referrals now plan instead of declining. Then the crawled pages turned out to be roughly **a sixth site navigation**, trimmed away, which promptly broke a golden negative that had been passing only because junk chunks were crowding real ones out of the candidate pool. A test that passes because of garbage is not a safety property, so the leak was fixed at its source. **Corpus growth spends the threshold margin**, exactly as [ADR-0009](../40-adr/0009-local-reranker.md) warned, and three drafted negatives that leak are recorded with their scores rather than filed or deleted.

**A corpus of 17,000 words was refusing most of what it was asked, and both halves of that are now addressed.** Measured on the live database rather than estimated: seventeen documents, of which the thirteen we wrote came to **7,443 words**, some as short as 364. Every gate was working exactly as specified, so the refusals were true statements, and the dominant one was not the ranking threshold but the groundedness gate asking whether concrete steps could be written quoting only these sources, to which a 500-word principles document honestly answers no **even about its own topic**. The documents are now 1,300 to 1,900 words each, **20,946 in total**, deepened rather than widened on purpose, because every leak this project has measured came from a document written in general marketing vocabulary while a document that says more about its own subject competes only for its own topic. No titles changed, no platform is named anywhere, and the five golden negatives were probed through the real pipeline before the gate: all five still return nothing, the closest at 0.77x of the threshold. **And the eval's own green metric turned out to be the gap list.** `--gate` reports "blocked 1.00 of scope negatives" as a pass over webinar funnels, conversion tracking, app-store ranking, ad specs, influencer platforms and affiliate networks, every one of which is a reasonable thing for a founder to ask. So two things landed beside the corpus. **Every refusal is now written down** in `retrieval_gaps`, with the groundedness gate's own sentence naming what the sources lacked, which turns corpus growth from the author's intuition into a ranked queue; the write is fire-and-forget and the goal is scrubbed of identifiers first. And **a fourth core answers what the gate refuses, where refusing was the wrong product** ([ADR-0021](../40-adr/0021-a-labelled-ungrounded-tier.md)): a non-regulated marketing question that is in-domain and uncovered is answered from general practice, labelled by code rather than by the model, uncited, and structurally unable to propose a plan, so it cannot become a step that spends money. Legal, tax, permit and the regulated corners of marketing are declined in code and fall back to the refusal, and the share of ungrounded answers is a corpus-health number that should fall rather than a feature whose usage should grow.

**And what a campaign spent is now recorded, which closes the last of the four marketing tables and opens the flywheel's outcome half.** `campaign_outcomes` had carried its guards and its unique key since the domain landed, with no writer at all: the metrics sweep is that writer, riding the same ticker pass between publishing and crawling. The interesting half is that the table's own constraints decided the design rather than the other way round. It is **append-only by grant including for `service_role`**, so there is no UPDATE to fall back on and `insert ... on conflict do nothing` is the only idiom available; the unique key dedupes only windows that match **exactly**, which makes "what counts as a period" a correctness property rather than a formatting one. So a period is a **whole closed UTC day and never today**, produced by one pure function and nothing else: a partial day could never be revised into a whole one, and the next pass asking for the whole day would append an overlapping row rather than replace it, doubling the spend the optimizer reads. Days are pulled **oldest first, stopping at the first failure**, because the cursor is `max(period_end)` and writing a later day while an earlier one failed would move the cursor past it permanently. **Nothing here pauses, scales or closes anything:** a read has no terminal state, there is no campaign arc a failed measurement could take, and pausing somebody's spend because we could not read a number would be the worst available use of an uncertain measurement. Reading a campaign needs `ads:read` and deliberately not the publish scope, since a person may untick `ads:write` on a consent screen and a campaign that is already live is the worst moment for its numbers to stop. The **panel shows the figures in the same slice**, because `ProjectDetail.campaigns` was itself fetched-and-never-rendered and shipping a writer with no reader would have extended this repository's most-repeated defect rather than closed it; null renders as "No numbers yet" and never as `0`, since a zero claims a day was measured and found to have none. `20260829160000` adds the `source` check constraint the table shipped without, in the same change as its first writer: `source` is part of the unique key, so a value like `metrics` would collide with nothing and a typo would look like a label mistake while behaving like a duplicated payment record.

**And a campaign that spends past what a conversion is worth is now paused without anybody clicking, which closes the loop the last slice opened.** The metrics sweep recorded spend and deliberately stopped ("acting on a CPA ceiling needs a ceiling, which has no writer yet"); the ceiling has its writer now, and **the ceiling is the authorisation** ([ADR-0014](../40-adr/0014-cpa-ceiling-authorises-auto-pause.md)): the owner types a cost-per-conversion figure on the panel, the model never proposes it, and the next sweep pauses any live campaign whose measured whole days breach `spend > ceiling × (conversions + 1)`, an inequality chosen because it needs no division and abstains loudly on anything unmeasured, since judging an absent conversion count as zero would manufacture the worst number out of not knowing. **NULL abstains rather than blocks, deliberately inverting the budget columns**, and a ceiling of 0 is refused at contract and table both as a kill switch wearing the shape of a threshold. The crash ordering **inverts ADR-0013 and says why**: publish records intent first because the platform invents an id an unrecorded crash would lose, while a pause creates nothing and re-derives from durable rows, so the platform is called first and everything converges, where our-rows-first would open the one unacceptable window, a database claiming `paused` about a campaign still spending. The idempotency keys **carry an epoch** counting prior resume transitions, because a key derived from the campaign id alone would let a record-replay platform answer a post-resume second breach with the first pause's recorded success while the money kept moving. No failure moves a campaign anywhere (`live -> failed` is not a legal arc, pinned in pgTAP), an expired connection is announced because "your spend cannot be stopped" outranks "your numbers stopped", and **resume ships in the same slice** because an auto-pause with no way back is the dead-end shape this repository has recorded three times: owner-only, from the panel, with the warning before the click that a still-crossed ceiling re-pauses on the next check.

**And the marketplace has its domain now, which is where the last live dead end starts closing.** `escalated` means "an expert should do this"; `router.ts` sends every human-owned step there saying it "goes to the marketplace", and the marketplace does not exist. **Twelve tasks are sitting in that state on the live database.** `20260827120000` measured seventeen, gave the owner a way to take such a step on themselves, and said in as many words that it was not the marketplace and must not be dressed up as one. Four tables land with their guards and **no writer at all** — the marketing domain's ordering repeated, because the recorded failure here is the other order five times over, most recently a role-escalation guard that existed only as a sentence in a comment for forty-four migrations and which is fixed in the migration immediately before this one, precisely because `human_node` is about to mean "eligible for paid work funded from somebody else's authorised budget". **Three of the module's nine entities land and a fourth the module never named**, forced by the others: once a node can read their own profile, a face-search result cannot live there, because it names a third party the node may be a duplicate of and carries scores used to decide against them, and RLS filters rows rather than columns. So `node_verifications` gets no policy and no client grant at all, refuses `permission denied` rather than zero rows **to the subject of the record**, and is append-only including for `service_role`. The rest is stated rather than glossed: **PostGIS is not enabled** and service area is a hierarchical jurisdiction code, because the matching rule the module specifies is a containment test plus a specificity ordering rather than a geometry query, and a text corpus beside a geometry node is the two-representations defect that already cost forty-seven tasks their visibility ([ADR-0015](../40-adr/0015-service-geo-is-a-jurisdiction-code.md)). **An engagement will carry no state of its own** ([ADR-0016](../40-adr/0016-an-engagement-has-no-state-of-its-own.md)): every state in its lifecycle is already a `task_state` with its arcs already enforced against `service_role`, and a second enum would drift silently, because a disagreeing engagement is a confusing screen rather than an error. **Nobody is admitted to any room**, which is load-bearing: there are no threads, so room membership would show a node the whole DAG, and the sequence puts threads before any writer that could admit anyone so the narrowing is never actually taken.

**And chat has threads now, which is the narrowing this repository recorded twice and never took.** `escalated` sends human-owned work to a marketplace that does not exist, and the reason no node can simply be admitted to the room is that room membership is coarser than the access a node should have: it would show them the entire project DAG. `room_members.scope` was the column that was supposed to fix that, and it had sat there since the second migration as unconstrained text with **no check, no policy, no helper and not one reader** for forty-four migrations. It is the fifth member of the family this repository keeps recording, and the second of the worst-shaped kind, the kind that announces itself as a control rather than as an absence, because it shipped beside `expires_at`, which _is_ enforced everywhere. Four migrations land `threads`, `messages.thread_id` and `scope` with teeth, and **grant nothing**: no route, no writer, no client write grant, so a thread cannot be created and nobody can be admitted to one. A thread-scoped member will see the room shell, their own thread, its channel and only messages carrying their `thread_id`, **never the null-thread room stream**, which is the owner's conversation with the AI. Three things fall out that were not in the plan. `private.is_project_member` now requires room scope, so a thread-scoped member is not a project member at all, because task-level visibility joins through `engagements`, which does not exist, and a policy that cannot yet be written correctly is not written approximately. `private.shares_room_with` was **a leak nobody had named** in either of the two narrowing comments: it would have handed an admitted node the profile basics of every member of the whole room, and it is now closed on both sides, with the owner-sees-their-node half booked as a named obligation on the engagement slice rather than approximated. And **the suite caught a policy rather than confirming one**: `room_members` is the single table where the rows _are_ the scopes, so the predicate that is right for `messages` asks a different question there, and a thread-scoped member could read every membership row pointing at their own thread, including that of a node whose access had already lapsed. It asserted 1, measured 2, and the correction is its own migration rather than an edit to the applied one. **Realtime was extended, not replaced**: both policies gained the scope conjunct in place so the time-box survives, and there are deliberately no thread topics yet, because a branch with no broadcaster and no subscriber would be a third guard with no writer in the slice whose whole subject is that anti-pattern. Until they land, a thread-scoped member has no socket and reads the since-cursor `GET`, so the failure mode is a delay rather than a disclosure.

**And a step that needed an expert can now reach one, which closes the last live dead end in the product.** `escalated` means "an expert should do this", `router.ts:93` has sent every human-owned step there since the router landed, and the only exit was the owner taking the step on themselves. **The owner clicks "Find an expert"** and the ticker offers it to one ranked node at a time; a decline or a 48-hour expiry cascades to the next; exhaustion returns the step with a message naming it. **The dispatch is a person's click rather than a sweep**, which is the load-bearing choice: twelve tasks sit in `escalated` on the live database, and a sweep claiming them all on deploy would have pushed a dozen steps at a cold-start pool while removing the two controls that already worked. **`offers` is the first table in this domain to land with its writers** rather than ahead of them, inverting the ordering the other four followed, because `20260831120000` deferred it by name on the grounds that "its entire content is a lifecycle" and a transition map nobody can exercise is the `ad_entities` mistake. Two decisions are booked rather than drifted into. And **thread creation, booked here since the threads slice, moved to acceptance**, because slice 4 admits nobody and a thread would be a row with no reader. What the matcher can rank on is much less than the module doc specifies and the gap is said out loud: `trust_score` is NULL on every row, `completed_engagements` is zero, and **no skill or licence can be verified at all**, so the pool matches claims and ranks on price with a deterministic tiebreak, which is honest where a weighted score over constant columns would be arithmetic pretending to be a ranking. `tasks` carries no `required_skills` and never did, so a **reviewed stage-to-skill map** answers it from the one field the planner fills in, rather than asking a model to decide who gets paid or asking the owner the question they escalated because they could not answer. **Nobody sees an offer but the node it was made to**: one policy, and the owner reads zero rows, because an offer names a node and that pair stays closed until the engagement slice opens it deliberately. **Accepting is refused by the lifecycle map and disabled with its reason printed**, since accepting is inseparable from funding escrow and escrow is the next slice.

**And that expert can now take the work, be paid from the budget the owner authorised, and talk to them about it.** Accepting was refused by the offer lifecycle map and the button was disabled with its reason printed, because accepting is inseparable from funding escrow: `claimed → escrow_funded` is the task machine's only exit from `claimed`, so an accept that wrote no ledger row would leave somebody holding work nobody had paid for. **It is one database function.** `accept_offer` settles the offer, walks the task twice, freezes the price into an `engagements` row, models the money against `projects.budget_ceiling`, writes a balanced double-entry pair, creates the task's thread and admits the node to it, in one transaction, because written in Node it would be nine statements that can half-happen. **Nothing is charged**: the only registered payment provider is a deterministic in-repo fake, `carriesRealMoney` refuses any other before an rpc is made — the third flag of that shape after tokens and identity documents — and the counsel gate in payments-billing.md is unmoved, because modelling an obligation is not money movement. **Three obligations booked by earlier slices land with it**, all named in advance rather than discovered: the thread writer that `threads` shipped without, the counterparty pair that three migrations refused to approximate and which now joins through `engagements` (`ended_at is null` is the entire time-box, so ending the deal closes it again), and the `author_kind = 'node'` writer, answered as **their own grant on the existing client path** because a server-mediated route would be a second write path to keep in step. **Two bookings were reversed and each has an ADR.** The slice table said this slice would restore `claimed → matching`; it does not, because accept and fund are one transaction so `claimed` is transit-only and the arc has no producer ([ADR-0019](../40-adr/0019-claimed-to-matching-stays-dropped.md)), which makes **five consecutive slices that restored no arc** and says the machine was drawn wider than the product has needed. And `projects.budget_ceiling` now has **two classes of committer** rather than one, so four places compute that sum and must move in step, each pinned by a suite ([ADR-0020](../40-adr/0020-the-ceiling-has-two-committer-classes.md)). One limit is a product decision rather than a gap: `room_members` is keyed on `(room_id, user_id)`, so a node works **one step of a project at a time**, and the second acceptance is refused with a sentence rather than absorbed silently. And a hold on a step that is later cancelled would pin part of somebody's budget forever, so `held → refunded` ships with its producer: a reconcile sweep that gives the money back, ends the engagement, revokes the thread membership and says so in the room. It deliberately never touches a step that reached `done`, because that would be taking back money somebody earned.

**And the work actually gets done, reviewed and taken back if nobody does it.** `escrow_funded` had been where a funded step stops, because `escrow_funded → in_progress` had no producer: a node accepted, the owner's budget was committed, a thread existed, both people could talk in it, and nothing could happen to the work. The node **starts the step, hands it over with a note and files, and the owner approves it or sends it back**. The core loop needed **no migration at all**, which is what guards-before-writers is supposed to produce: every arc it walks was declared by `20260813120000` and walkable by nothing. **`tasks.acceptance_criteria` gets its first consumer** since it landed, as the one thing the deterministic floor check can actually check, and the check **cannot reach `approved`**: it returns the step to the node or passes it to the owner, because the AI does not decide that a person's work is finished and therefore that they are owed money. **Proof is an `artifacts` row rather than a second table** ([ADR-0022](../40-adr/0022-proof-is-an-artifact.md)), reversing a booking both entity tables carried: a second table would strand an unremovable enum value and duplicate five guard and reader surfaces, and EXIF belongs to a verdict table when an extractor exists. **A thread-scoped node still reads nothing through a policy** and slice 6 added none, so their proof comes back through a service-key projection after a caller-scoped read of their own engagement, which is the only shape the storage half permits at all. **And a step somebody took and abandoned goes back to the market** ([ADR-0023](../40-adr/0023-a-breached-deadline-reassigns.md)): the deadline is frozen onto the offer before the node accepts, they are warned once a day out, and `reassign_engagement` then unwinds the deal in **one transaction**, because a live human is one of the actors in the window and every partial state either double-commits the ceiling or takes money from somebody still working. Its task move is conditional and **raises on zero rows**, so a node who handed over in that window wins. It never touches a step already delivered, enforced in the map and in the sweep, since a deadline passing after the work arrives is the owner's failure to review. **Two arcs restored after five slices restoring none**, both with their producer in the same push, and one defect fixed with them: `cascadeRound` counted only `offered → matching`, so a reassigned task would have re-derived the round its no-show already held, collided, read back that **accepted** offer and dispatched a third node against it, which is the second objection [ADR-0019](../40-adr/0019-claimed-to-matching-stays-dropped.md) raised arriving exactly as predicted. **A thread has its own realtime topic now**, emitted beside the room's rather than instead of it, so the node stops polling and the owner keeps receiving thread messages live.

**And the expert gets paid, which is the last link in the loop and the first state anything in this system has ever reached the end of.** An owner approved an expert's work and the step stopped at `approved`: the hold still said `held` and still committed part of the budget, `held → released` was declared with nothing able to walk it, `engagements.outcome` never reached `'completed'`, and `completed_engagements` — the number slice 8 ranks and rates on — was zero on every row in the database. **Approving the work is the payout authorisation** and there is no second button, on [ADR-0013](../40-adr/0013-approving-a-campaign-publishes-it.md)'s argument and on the money flow payments-billing.md already specified: the owner authorised that exact figure when the escrow was funded at acceptance, has seen it on the step, and has just read the proof. The next ticker pass transfers and `settle_payout` settles everything else **in one transaction**, because every partial state here is a money defect somebody reconciles by hand — a released hold under a live engagement, a released hold with no ledger pair, a finished step whose hold still pins the ceiling. **Four migrations and no `task_state` migration**, which is two consecutive slices where the answer to "which migration adds the arc" is "none": `approved → payout_pending → paid → done` were all declared by `20260813120000` and walkable by nothing. The ordering **takes ADR-0013's and not ADR-0014's**, and the reason is the same one that made those two disagree: a transfer _creates_ something under an id the provider mints, so the intent is written first and each of the four crash points resumes, where a pause creates nothing and calls the platform first. **`done` gets its first producer ever, on the human arm only** — nothing here had ever reached a terminal success state, and an AI step still stopped at `approved` and was still cancellable, which was written into business-projects-workflow.md as that module's gap rather than closed from a marketplace slice. **That module has since closed it**, in the slice below. **The take rate is not deducted** ([ADR-0024](../40-adr/0024-the-take-rate-is-not-deducted-from-an-agreed-price.md)): escrow holds exactly the price the offer showed the node before they accepted, so a fee taken at release would mean every surface showed somebody a figure and then paid them a different one, and `platform_fee` lands as a column written from a constant zero until the offer can name it. One cost was **discovered by building rather than booked**: ending the deal is what pays somebody, and `engaged_counterparty` was time-boxed on `ended_at is null`, so paying an expert would have erased their name from the owner's panel at the exact moment slice 8 is about to ask the owner to rate them; the pair now survives an outcome of `completed` and only that one, because a cancelled or reassigned deal delivered nothing and there is nobody to rate. **Still nothing is transferred** — `carriesRealMoney` is now checked at two writers rather than one, it throws rather than counting so a refused pass is inert, and there is deliberately no `payout_account_id` column waiting for a Connect Express onboarding that does not exist yet.

**Not built, and not claimed:** a **thread switcher in the owner's UI** (thread messages are marked in the stream rather than hidden, because hiding rows the owner may read is the defect this repository has recorded twice); and **an extension to a deadline** (a node can ask for longer in the thread and the owner has no way to grant it, because an extension writer needs a surface, an authorisation question and an audit story, and inventing all three alongside the column's first producer is how a control ships without its reasoning). **The corpus is externally cited now.** A checked-in source registry, a guarded fetcher, page-hash change detection and a cadence re-crawl sweep on the existing ticker put four real documents beside the thirteen we wrote, each carrying its publisher, its address and the date we read it, so a citation on the plan card is a link a reader can open. The measuring is the interesting half, and it removed more entries than it kept. Nine pages were registered and seven answered, but three of the seven were site navigation rather than a document, one of them localised to the crawler's own IP and stored as a Facebook menu in Georgian: **a status code is not evidence a page is a document**, so every entry is verified by reading what it stored. A fourth was removed by the eval rather than the fetcher. Meta's advertising standards fetched perfectly, and a 25-chunk policy hub written in general marketing vocabulary turned out to act as a magnet: it caused the retrieval gate's only leak, and on an unrelated legitimate question it took five of the top eight results while the document that actually answers that question took none. **Fetchability and usefulness are separate questions**, which is not obvious until they disagree. Two families stay uncovered and are named rather than implied: the FTC blocks our declared crawler, which we are not going to disguise, and no EU-official page was found that this fetcher can read. **Retrieval no longer depends on a paid provider at all.** Reranking moved in-process onto `bge-reranker-v2-m3` ([ADR-0009](../40-adr/0009-local-reranker.md)), matching the hosted reranker on the golden set (recall 1.00, coverage 1.00, zero leaks). That only became possible after fixing four defects in our own pipeline, which had made two standard models look unusable: decomposition emitted the maximum sub-queries on every goal, those sub-queries ran 20-30 words at a cross-encoder trained on six, one was generated every time for a funnel stage the corpus has no document for, and 40 candidates were reranked against a 43-chunk corpus where RRF already ranked the answer 1st to 3rd. Rerank calls per eval run fell 87 to 49 with identical results, and a goal went from 265s to 71s. The remaining cost is CPU: plan latency now scales with the cores the AI service is given, and runs are asynchronous so that is a wait rather than a failure.

**And when it goes wrong, somebody can now say so and somebody can decide.** `disputed` had been declared since the workflow domain landed, narrowed to one unusable inbound arc by a rewrite doing something else, and refused by name in every marketplace slice since — because "a `disputed` task nobody can move is the `escalated` defect on purpose", and this repository had already measured that defect at twelve stranded tasks. Slice 8 restores **all four** inbound arcs together, adds `disputed → matching`, and builds the console that makes them safe ([ADR-0026](../40-adr/0026-the-dispute-exit-map.md)). **The freeze is one statement and there is no flag:** `PAYABLE_TASK_STATES` is `('approved','payout_pending')`, so moving the step to `disputed` is what stops the money, and a flag beside the state would be a second thing the sweep has to remember to read. **Both parties can raise**, and the node's arc from `rejected` is the only act in this system a node performs against the owner — without it, an expert whose work was wrongly sent back could only redo it or stop answering, and stopping is what the no-show sweep reads as _their_ failure before reassigning the step away from them. An operator resolves it five ways, and every consequence lands in one transaction: the task arc, the escrow settlement, the engagement outcome, the thread roster, any orphaned payout, the decision and the trail. **A partial settlement is a full refund plus a new hold released inside that transaction** ([ADR-0025](../40-adr/0025-a-partial-settlement-is-a-refund-and-a-new-hold.md)), because both escrow settlements are terminal and neither reaches the other — eight ledger entries across two holds, four each, and because no second `held` row is ever visible outside the transaction, the four places that compute a project's committed budget needed no change at all. **`released` moves no money here**: it returns the step to `approved` and the existing sweep pays, reusing the recovery path built for a crash rather than opening a second way to pay somebody. `/ops` is the first ops surface and the first legitimate reader of `ledger_entries`, a table that has had RLS with no policy and no client grant since the ledger landed precisely because "the reader of raw entries is the ops console". **`profiles.role` gets its first reader in forty-six migrations**, and it is read from the database and never from the token: the JWT does not carry it, so a check against the claim would refuse everybody while looking like a working deny-by-default. A role is minted only by a script somebody runs with the secret key. **`trust_score` stops being NULL on every row**: two-sided ratings land, and the score is `avg/5` over ratings received and deliberately nothing else, because three of the four inputs the spec names cannot be computed in a build whose KYC is a fake and whose credentials can never be verified. A `disputed_resolved` deal is **readable and not rateable** — both parties keep the record, and the trust graph does not take a score from a deal an operator had to decide. **Node suspension is not built**, on this slice's own argument one table over: it would be a terminal state with no exit until a moderation console exists.

**And somebody is finally told.** Every marketplace slice from 4 to 8 closed on the same sentence, and slice 8's was the plainest: "nobody is notified of anything, still". That was not a missing convenience: `OFFER_TTL_MS` is 48 hours and `WORK_TTL_HOURS` is 168 **because** nobody is told, and `matching.ts` says so in as many words, that "anything shorter would expire against people who had not looked yet". The marketplace's deadlines were set by the absence of a doorbell. Eleven moments now derive an inbox row for the person they concern, and **the row is derived from `public.events` by a trigger rather than written beside each act** ([ADR-0028](../40-adr/0028-a-notification-is-derived-from-the-event.md)), because **six of the eleven are written by SQL functions** — `accept_offer`, `reassign_engagement`, `settle_payout`, `raise_dispute` and two guard triggers — that a helper called from `apps/api` reaches only by re-implementing their transactions in TypeScript. Deriving from the one ledger all of them already write buys the property the slice exists for: a moment cannot be recorded without the person being told, including by a writer that does not exist yet. The accepted cost is stated rather than discovered, since that trigger runs inside `settle_payout`: a defect in it aborts a payout, which is why every enrichment is a left join, the verb list is a closed `case`, and the pgTAP suite derives a row for every verb. **The dedup key lives on the notification because `events` has none**, and a replay writing the same moment twice is a thing this repository has already had to write code around. **Copy is not in the database:** the row stores the facts a sentence is made from and TypeScript composes the words, which is what makes rule 22's ban on em dashes in notification copy a unit test over every kind rather than something a reviewer has to notice in a migration. The payload is an **allow-list rather than a copy**, and that is a disclosure decision: forwarding the event's payload wholesale would have shown both parties `resolved_by`, the operator who decided their dispute. Delivery is a **third Realtime topic**, `notify:user:<uid>`, as its own policy rather than a third disjunct inside the two chat policies — what `20260906120000` refused to duplicate was the `expires_at` time-box, and a per-user topic has no membership row and no time-box to keep in step. **Only in-app is built.** Push, email and SMS each need a paid provider; preferences, digests and `delivery_log` wait for them. The 48-hour and seven-day windows are **unblocked and unchanged**, because shortening them is a decision about time zones and about what somebody asleep is entitled to, not a side effect of building a bell.

**And a step that is waiting now says what it is waiting for, which is the first thing this panel has ever said about the shape of a plan.** The DAG has had edges since `20260828120000` and no surface could mention them: a step waiting on another rendered as "Not started", the same sentence a step that is merely next in the queue gets. Measured on a live project, that was twelve of fifteen steps reading identically, in the one situation where the owner has something to do, since the way to unblock five steps is to deal with the one they all point at. `Task` carries `blockedBy` now, **resolved on the server rather than shipped as ids**: sending edges would have put a second copy of `private.task_deps_satisfied` in a React component, where it would drift silently, because a step wrongly described as blocked renders as a perfectly plausible sentence either way. **That rule had already drifted, one table over** — `DONE_STATES` claimed in its own comment to mirror the SQL and was missing `payout_pending`, so for the whole life of the payout slice a step between "the owner approved it" and "the transfer landed" was counted as unfinished on the project list while the panel beside it read "Done, payment pending" and the scheduler let its dependents run: three surfaces, two answers, nothing failing. **A cancelled dependency is a dead end, not a wait**, and reads as one, because `tasks_ready` can never clear it and the plan has to change; the variant is weight rather than the stopped badge's red, since `--red-500` measures **4.00** as text on the light panel and fails AA, which is the fifth token in this system to be chosen by eye and measured wrong, and the first to be measured before it was spent. **And the same slice gave the AI arm a terminal state**, which the payout slice had named as this module's to produce: `approved` is not terminal, "anything non-terminal may be cancelled" is a universal rule of the map, and a step that produced its artifact and passed its own check could still be cancelled by a replan and recorded in the audit trail as abandoned. `executeTask` and both owner-answer paths walk on to `done`. **No migration**, for the third consecutive slice: the arc was declared and unrestricted by `20260813120000` and simply had no walker. **The second write is conditional and a miss is a race** rather than a defect, since `approved → cancelled` is legal in exactly that window, so a lost race delivers nothing instead of announcing work that was cancelled. **`approve_work` deliberately does not finish the step**, because `PAYABLE_TASK_STATES` reads `approved` and walking it on would take the step out from under the sweep that pays the expert; the sixty-six historical `approved` rows are **not backfilled** for the same reason. Driven against the live database rather than a stub, because no route test here can fail on a select string: the exact select, the enum filter and the id scoping all answer 200, the owner sees all fifteen edges through RLS rather than zero, and the real helper on real rows produces both sentences. **Not exercised in a browser**, and the reason is recorded rather than glossed: a second API against the live database would have fired a ticker pass with no AI service reachable and escalated live tasks.

**And a question is answered on the card, which is the first time the product has asked for less than a paragraph.** Intake's questions went out as plain text and came back as one chat message the owner composed to answer all of them, which a model parsed back into slots; while the card waited it **claimed every message the owner wrote** for two hours, because that was the only way to know which message was the answer, and two cards were found holding rooms for nearly two days. The card renders now ([ADR-0029](../40-adr/0029-a-question-is-answered-on-the-card.md)): a budget band or a timeline is a row of chips, an audience or an offer is a short field with its own Save, a step the plan asked about is one field, and each answer is its own embed action through the same route every other card is acted on through. That is what makes `required_role` the enforcement rather than a hint. **Every chat message is a goal again**, an owner's new goal dismisses the intake cards about the previous one and never a task card, the `new goal:` escape and the two-hour window are gone with the trap they escaped, and `decideIntakeTurn` with them. Each answer is **one statement** in Postgres, `jsonb_set` under the row's own `state = 'pending'`, so two chips clicked in the same second cannot lose one another; the card closes itself when the last required slot lands, or when the owner says to plan with what they have said, and the run continues from what it collected. The action response carries the card's new payload, which closed a second defect on the way: a campaign approved at 2000 had read "approved at 0", because the cap the route wrote never reached the card. **And the plan no longer waits for the card.** Intake posts the questions, the room reads "Working on a plan for: ...", and the same run plans from what is known, so a plan with visibly empty stages arrives beside the questions instead of after them. Finishing the card continues that run under a deterministic id: a plan nobody approved yet is moved to `expired` only once its replacement exists and the new card names it, and a plan already running gets a `replan` card through the same producer the panel uses, so nothing is applied without a card. **And the workspace remembers.** `room_profiles` holds audience, offer, budget band and timeline per room, written by the card, by the run and by an "About your business" block on the panel, each writing only the keys it holds, and read by the owner alone through the first owner-only policy in the database. Intake's first round is seeded from it, so the second goal in a room asks nothing; `merge_slots` in the reasoning core had to let a newer statement replace an older one for that to be safe.

**And the agent stopped being one anonymous account, which is the first time the chat has said who is speaking.** Since `20260728120000` every AI message was `author_id = null, author_kind = 'agent'` and the client rendered all of them under one hardcoded name, so the plan, the intake questions, a delivered landing page, a campaign proposal and a notice that a campaign was paused for crossing its cost ceiling all arrived from the same account, and `events` recorded the same flat answer for each. `messages.persona` (`20260912120000`) names one of four voices, **Strategist, Content, Ads or Analyst**, chosen in `apps/api` by `personaForStage` from the step's own `tasks.stage`, a column the planner already fills. **A persona is a voice and never a writer** ([ADR-0031](../40-adr/0031-an-agent-persona-is-a-voice-not-a-writer.md)), which was the whole risk in the request that started this: the shape most multi-agent products take is several agents that each plan and each spend, and this system's guardrails all assume the opposite, since three campaigns of 400 pass a 1000 ceiling individually and commit 1200 between them. So nothing about who may act moved. One writer to the task DAG, one `routeTask`, one `checkSpendCap`, one `apply_plan_diff`, and no model chooses the label. **`text` with two named checks rather than an enum**, on ADR-0022's argument that an enum value cannot be dropped and this set is expected to move in both directions: `messages_persona_known` closes the set and `messages_persona_agent_only` refuses a persona on a system notice or, worse, on a person's message wearing an AI's name. **The insert policy gained one conjunct and had to be retyped whole**, because `alter policy ... with check` replaces the expression rather than appending to it, and a conjunct dropped in the retyping would read as the chat quietly breaking rather than as a security change; `message_persona.sql` asserts the two capabilities that restatement could have taken away, and `thread_scope.sql`'s three write assertions were re-run against the applied schema for the same reason. **What stays `system` became a rule rather than a habit**: system says what a person or the platform did, a persona says what it did or found, so an offer accepted, work started, a dispute, a payout and a failed run are unsigned, and `postSystemMessage` and `postPersonaMessage` are two functions rather than one with a nullable argument so a caller has to decide. **Conversion belongs to Content and the Strategist is the fallback**, both decisions rather than defaults: a landing page is a piece of writing before it is a channel, and `tasks.stage` is free text, so an unrecognised or missing stage is exactly the moment nobody has decided what kind of work this is. `personaForStage` is total and never throws, because a thrown label would mean delivered work that never reaches the room, which is the failure `roomForProject` already exists to fix. **Nothing was backfilled**, so an old room renders `Octopus` forever; choosing a specialist for a message written before specialists existed would put a guess into the record a person reads to reconstruct what happened. **`services/ai` is untouched** and all five prompts still open "You are Octopus", because a persona changes attribution rather than wording, so there was no prompt change and no eval to gate. **The control run is what makes the suite worth having**: run without the migration, 7 of its 10 assertions fail and the 3 that pass are precisely the regression ones, which is the difference between a suite that tests the change and a suite that tests its own fixtures. The live run found nothing wrong and proved the two halves that no test in this repository can reach: a goal posted through the real stack produced a `strategist`-signed started notice where a muted system line used to be, then a `strategist`-signed plan card, while a `persona` forged into the POST body came back null.

**And the four voices joined the members panel, where the only honest thing to show turned out to be a step title.** The panel listed people and nothing else, so a room with a step running looked exactly like an idle one and the AI existed only as messages after the fact. `ProjectSummary.working` now carries the stage and title of every task the executor is holding, computed by the same pure summariser the progress counts come from and riding the project list the client **already** refetches on every message, because the things that change it all announce themselves in the room. That is the whole mechanism: no polling, no second subscription, no server-side agent presence table, and the panel moves when something actually happened. **`WORKING_STATES` is two states rather than one**, since the critic reading a draft is still the agent busy on that step from the reader's side and stopping at `ai_running` would blink the panel off between the draft and its review; `routing` is excluded because the scheduler is still deciding who takes it and no voice owns it yet. **The wire carries the stage rather than the persona**, so the client maps it through the same registry it renders names out of and there is no second copy of `personaForStage` to go stale the first time a stage moves between voices. **The pulse is the second use of the one reserved glow** and means what it has always meant, with the activity line carrying the same state in words so nothing rests on colour or motion. **A separate `UiPersona` rather than a widened `UiMember`**, because a persona has no user id, never goes offline and never expires, and widening the member type would have forced four literals elsewhere to carry fields that mean nothing for a person. **The Strategist's busy state is the one thing here that is a claim rather than a reading**, and it is marked as such: planning happens before a project exists, so the longest wait in the product has no row to be found, and this browser sets the flag when its own run is accepted and clears it on a Strategist message, a system notice, or after three minutes. The timeout is not a fallback for a bug. A run can end in ways this client never sees, so a pulse with no way to stop would be a lie that outlives the thing it described; a tab backgrounded through a whole run still pulses until it expires, which is written down rather than solved by matching on text. The live run found nothing wrong and showed the thing working on real rows: Content on "Build landing page copy around message match" and the Analyst on "Measure email by clicks and revenue, not opens", both with `animation-name: breathe` and the glow shadow in computed style while the two idle voices stayed a plain green dot, and the project panel's step lines reading "Content" and "Ads" where they had read "Octopus".

**And you can now address one of the four by name, which is the first time a sentence in the chat has been aimed at part of the system rather than at all of it.** The idea this came from was nine bots that each plan and each act, and that is the shape the whole slice was built to refuse: this system's guardrails all assume one writer, and three campaigns of 400 pass a 1000 ceiling individually while committing 1200 between them. So `@Ads move the budget to Meta` does not move a budget. `startRun` parses the mention **before anything else it does**, resolves the project running in that room, posts one acknowledgement in the voice addressed, and calls the same `produceDiff` an owner's own request from the project panel takes; the owner approves the card or does not, and `apply_plan_diff` behind that card is still the only thing that changes a running DAG. **The branch runs first for two reasons that are easy to get wrong.** A new goal closes the intake cards that were sharpening the previous one, and a mention is not a new goal, so closing them would throw away questions somebody is part-way through; and sending "@Ads" to the classifier would spend a call to learn nothing. **`@Strategist` routes the same way**, deliberately: a fresh intake on a running project produces a plan competing with the one already executing, which is exactly the regeneration replan-by-diff exists to prevent, so the Strategist answers by diff like everybody else and skips the line it would otherwise be saying to itself. **A member's mention is still an ordinary goal**, because the cards are about the owner's own business and a member's sentence is not an authorisation. **The grammar had to live in `packages/contracts`** rather than in core, because two independent readers must agree on it: the composer decides what to highlight and offer in the browser, and `startRun` decides what to route in Fastify, and a second regex would have disagreed at exactly the cases nobody tests, `someone@ads.com` and `@Adsy` among them. `@Octopus` is not a mention: it addresses the whole thing, which is what every message already does. **Enter completes the mention rather than sending**, which is the one failure the composer must not have. **`agent-runner.ts` got its first test file in its life**, which is worth saying rather than quietly fixing: it is the only path by which anything the reasoning core says becomes visible, and every test it had came from route suites that mock it out entirely. The eleven cases are as much about what does not happen as what does, and one of them was mutation-checked by breaking the persona argument and watching exactly the two discriminating assertions fail. The live run found nothing wrong and produced the more interesting half by accident: the reasoning core read the request, found sources that did not cover it, and declined to propose anything, so the room got an `ads`-signed sentence saying the plan is unchanged and why, rather than a card. That is the groundedness gate reaching a mention through a path nobody wrote for it, and it is the right answer.
