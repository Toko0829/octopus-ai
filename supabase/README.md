It adds the `question` component and the `answered` state that intake needs. Without them intake did not merely lose its card, it **did not run at all**: the agent run's first act is to read any open question card, that read filters on `component = 'question'`, and Postgres rejects a comparison against an enum value that does not exist. The degradation is deliberate, since an optional clarification step must not break a working path, but it means the only visible evidence was a planner refusal with no sign intake had been involved. Observed live: "Hello" came back as `refusing-ungrounded-v1`.

## RLS tests (pgTAP)

`tests/rls_membership.sql` covers the surface [security-compliance.md](../docs/10-architecture/security-compliance.md) calls the hardest: a room shared by an owner, an unexpired node, an expired node, and an outsider.

`tests/rls_workflow.sql` covers the workflow DAG: the same four actors against `projects` / `tasks` / `task_deps` / `task_runs`, plus the two triggers. It runs the state-machine and acyclicity assertions **as `postgres` on purpose**, which is the opposite of the rule for the RLS assertions and for the same underlying reason. RLS must be tested as a client because `postgres` bypasses it; these guards must be tested as `postgres` because they are supposed to bind trusted code too. If they ever start passing merely because the caller was privileged, the guard has been lost.

```bash
DATABASE_URL="postgresql://..." ./scripts/test-rls.sh
```

The script runs **every** `.sql` in `tests/`, rather than a hardcoded list, and does not stop at the first failing suite: a new suite that must be registered in two places is one that eventually runs in neither, and knowing whether a break is narrow or broad is most of the diagnosis.

`tests/materialise_plan.sql` covers turning an approved card into a project and its tasks. Its most useful assertions are the failure ones: every path that raises is also checked for **leaving nothing behind**, because atomicity is the reason that logic is one database function rather than a sequence of supabase-js calls.

`tests/artifacts.sql` covers the execution path. It asserts that the state machine **accepts the exact route the executor walks** (`ROUTING → AI_RUNNING → AI_SELF_CHECK → APPROVED`, plus the bounded re-do back to `AI_RUNNING`), which is much cheaper to discover here than at `ai_running` on a live project. Also that an artifact with neither body nor file is refused, and that a retry cannot overwrite the attempt it is retrying.

`tests/marketing_rls.sql` covers the marketing domain, and carries the one assertion in this directory that checks the **shape of an error** rather than a count: `channel_connections` must answer `permission denied` to a client, not zero rows. The grant absence is the control there, and through PostgREST a broken policy and a deliberate refusal are the same empty response, which is precisely how `20260827110000` hid for two weeks. It also asserts that `campaign_outcomes` refuses `UPDATE` to `service_role`, because append-only that only binds clients is not append-only.

`tests/project_membership.sql` covers the one that was actually broken: a room's **second** project. It asserts both directions deliberately, because the predicate it guards failed by returning nothing, and a version rewritten to return everything would pass any suite that only checks what the owner can see.

`tests/storage_artifacts.sql` covers the `artifacts` bucket. Its most useful assertion is the malformed path: an object whose first segment is not a UUID sits in the bucket while a member counts rows, and the listing must return a shorter list rather than an error. An inline `::uuid` cast in the policy would raise on it, and Postgres does not promise to evaluate the `bucket_id` test first, so one stray object anywhere in Storage could have broken every member's listing.

`tests/thread_scope.sql` covers thread-scoped membership (slice 2 of the marketplace sequence). Read it for the assertion that **caught a policy rather than confirming one**: `room_members` is the single table where the row is itself a scope, so the predicate that is correct for `messages` asks a different question there, and a thread-scoped member could read every membership row pointing at their own thread instead of only their own. The suite asserted 1, measured 2, and `20260901123000` is the correction. Its regression half is as large as its narrowing half on purpose, because a predicate narrowed one conjunct too far presents as "nothing loads" rather than as a security change.

`tests/node_onboarding.sql` covers the marketplace's first writers (slice 3): the KYC lifecycle map, `invite_node` and `decide_node_kyc`. It runs entirely as `postgres`, which is the right role rather than a shortcut: both functions are granted to `service_role` alone and the trigger they pass through binds every role including that one, so a suite running as `authenticated` would exercise a path nobody will ever take. Read it for the two assertions that matter most: **a node who never submitted cannot be verified** (`unverified → verified` is not an arc, so the route's ordering is enforced by Postgres rather than merely observed), and **a replay appends nothing and returns the same verdict**, which is what "derive the answer from the recorded rows rather than the payload" buys on a table with no `UPDATE`.

It is a separate file rather than more assertions in `marketplace_rls.sql`, whose `plan(46)` is exact and whose subject is deliberately "these tables have no writer". Two assertions in that older file did change, and both are edits the new map forced rather than fixes: its audit test now drives `unverified → pending` instead of `unverified → verified`, and its suspension assertion now passes for a second reason because no arc reaches `suspended` at all, so `node_profiles_suspended_has_reason` is unreachable until suspension has a writer. Both are noted in the file beside the assertions.

`tests/marketplace_proof.sql` covers the engagement loop and the no-show path (slice 6).
Read it for the assertions that pin **absences somebody could reasonably restore**: two arcs
stay dropped and each says why in its own message, and the most consequential assertion in the
file is a negative one, that neither new `-> matching` arc leaves from `proof_submitted` or
`in_review`. A deadline that passes after the work arrives is the owner's failure to review, and
reassigning there would take a finished person's fee and give it to a stranger. It also asserts
the race directly: a step handed over between the sweep's read and the call is refused, the raise
unwinds the whole transaction, and the delivering node's escrow is untouched.

**One of its assertions was inverted by slice 8 rather than deleted**, which is what that
wording was chosen for, and doing it cost more than it should have. The absence of a
`-> disputed` arc had been asserted inside a **four-way conjunction** alongside the absence of
`-> failed`; the `failed` half is still true and the `disputed` half stopped being true, and a
conjunction cannot be half-inverted, so the whole assertion had to be split and rewritten.
The general lesson, recorded in the file beside it: assert one fact per `ok` when the facts have
different lifetimes.

`tests/marketplace_engagements.sql` covers acceptance, escrow and the ledger (slice 5). Read it for the assertions that pin **absences somebody could reasonably "fix"**: `held -> released` is refused, worded descriptively because release is a payout act whose producer does not exist; `authenticated` has no grant on `ledger_entries` at all and the table carries RLS with zero policies, the `events` posture; and the project owner **still** reads zero offer rows, because an offer names everybody who was asked and the engagement names only the person who took the work. Every refusal is also asserted to leave nothing behind, since atomicity is the reason acceptance is one database function.

Everything runs inside a transaction that `ROLLBACK`s, so it is safe against a live database and leaves no fixtures behind. Verified green against the live database: `rls_membership.sql` 26/26, `rls_workflow.sql` 33/33, `materialise_plan.sql` 19/19, `artifacts.sql` 12/12, `room_sources.sql` 14/14, `document_supersession.sql` 9/9, `project_membership.sql` 13/13, `marketing_rls.sql` 42/42, `storage_artifacts.sql` 11/11, `materialise_campaign.sql` 44/44, `marketplace_rls.sql` 46/46, `node_onboarding.sql` 36/36, `marketplace_offers.sql` 37/37, `marketplace_engagements.sql` 70/70, `marketplace_payout.sql` 38/38, **`marketplace_disputes.sql` 62/62, `marketplace_ratings.sql` 24/24 and `marketplace_proof.sql` 35/35 (slice 8, re-run in full after the map changed under it)**, `thread_scope.sql` **14 of 54 re-run** (the eleven changed realtime and absence assertions, plus the three new owner-side ones, all green against the applied migrations; the other forty are untouched by those changes and were last run at slice 5, so a full-file run still wants a `DATABASE_URL`).

> **How the slice-8 suites were run, since there is still no `DATABASE_URL` here.** `scripts/test-rls.sh` needs `psql`; this machine has neither, so the three ran through the Supabase MCP, which returns **only the last statement's result set** and would otherwise show one assertion out of sixty-two. Each `select extensions.<assert>(…)` was rewritten to `insert into tapout(line) select extensions.<assert>(…)` against a temp table, with a final select reporting the count and every `not ok` line. **The count is the control**: it came back equal to `plan(N)` on all three, which is what proves the collector caught every assertion rather than silently dropping them and reporting an empty pass.

`tests/materialise_campaign.sql` is the one to read for the **spend boundary**, because that arithmetic exists twice by design ([ADR-0011](../docs/40-adr/0011-spend-cap-checked-twice.md)) and this is half of what stops the two drifting: it asserts that a campaign landing exactly on the ceiling is authorised and one cent past it is refused, which is the same `>` the TypeScript asserts in `packages/marketing/src/spend.test.ts`. It also pins the two filters both sides apply, that a terminal sibling holds none of the ceiling and a null-cap sibling contributes nothing rather than turning the sum into NULL. The assertion that found a real defect is the plainest one there: a card carrying no budget must create **no campaign at all**, where the first version of the writer created one holding `budget_cap = NULL` at state `ready`.

> **A fixture can fail an assertion that the code passes, and this suite did.** Its first draft pointed one room's `project_id` at the first project and then asserted that a third, card-less project was visible through that same column. A room has one `project_id`; it cannot point at two projects. Two assertions failed and briefly looked like a defect in the migration. Give each legacy-link case its own room.

> **A trap worth knowing when writing these.** Calling a function that inserts, from inside the `WHERE` clause of a select against the table it inserts into, returns NULL: the statement's snapshot is taken before it runs, so the new row is invisible to that same scan. It reads as the function returning nothing. Materialise into a temporary table first, then assert against it.

> **Run the advisors after any migration, not just the tests.** `20260813120000` passed all 33 assertions and still introduced six security lints, because the suite asserts the properties someone thought to assert and the advisor checks the ones everybody forgets. The worst of them was `task_deps_satisfied` being created in `public` as `SECURITY DEFINER` with EXECUTE granted to `authenticated`, which published the scheduler's READY predicate at `/rest/v1/rpc/`. That is lint 0028/0029, **the same one `20260728160000_harden_security_definer.sql` exists to clear**, reintroduced by someone who had read that migration. It looks like ordinary least privilege, and in Supabase `public` is the API schema. `20260813130000` moved the function to `private`, dropped it to `SECURITY INVOKER` (it is not used in a policy, so it never needed to bypass RLS), and pinned `search_path` on the four workflow functions that lacked it.

Two things it asserts that are easy to lose:

- **An expired node sees nothing at all.** Not the room, not the messages, not the plan card. Time-boxed access is the mechanism the whole marketplace depends on, and until this file existed the only evidence it worked was that nothing had visibly leaked.
- **Privileges, not only policies.** RLS filters rows a grant already permits, so a missing policy and a missing grant fail very differently. `TRUNCATE` is asserted explicitly because it **bypasses RLS entirely**, which is what made the default-privilege grant closed in `20260812120100` worth closing.

Tests run as `authenticated` with `request.jwt.claims` set, exactly as PostgREST would. Running them as `postgres` would prove nothing: that role bypasses RLS, which is precisely how a policy bug survives review.
