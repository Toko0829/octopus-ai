- **fix(ai): the database client had no retry at all, and one transient took the whole eval gate red.** Found on the first CI run of the Phase 2 branch. Shard 2 of 5 failed on `401 PGRST303 "JWT issued at future"` from `hybrid_search`; the other four passed, on the same static credential, in the same second. **That is what identifies the cause rather than leaving it a mystery:** the key is static, so its `iat` is byte-identical on every call and cannot be the variable. The clock is, across the PostgREST nodes Supabase serves from. One node with drift refuses some requests and not others.
  The real defect is the asymmetry it exposed. `providers.py` has had bounded backoff since the first armed eval run taught it that a `429` is not a transient `5xx`; `db.py` had **none**, so any single bad response ended the request. That matters more here than it looks, because `--merge` deliberately refuses to report unless every golden case is present: a lost shard is not a smaller measurement, it is a red gate. `_request` now retries transport errors, `408/429/5xx`, and `PGRST303` specifically. **Only that one 401**, because an ordinary 401 means the key is wrong and retrying spends three attempts to reach a slower, vaguer version of the same answer, which is the same distinction `providers.py` already draws. Kept as its own loop rather than shared with `_post_with_retry`, since that one is POST-only, raises a different error and carries Retry-After plus a rate-limit floor built for a metered API; merging them would parameterise away the distinctions both sets of comments call load-bearing. 238 Python tests (+6), sleeps captured rather than performed, including that a 204 still returns `None` through the rewritten loop.

- **build(ai): the reasoning core has a container, and the lockfile was carrying 2.5GB of GPU code for hardware nobody here has.** `services/ai/Dockerfile`, CPU-only, both model snapshots baked in. Sequenced now because `roadmap.md` defers sizing the AI instance to "a Phase 2 deployment decision, not an open question about whether it works", and you cannot size an instance you cannot deploy. **Measured on the built image rather than estimated: 6.44 GB of layers** (4.59 weights, 1.71 venv), **5.15 GB peak RSS** with both models resident, ~17s cold start to a warm `/health`, ~22s for the reranker's lazy first load. So the deployment floor is an 8 GB instance, and that is now a number rather than a guess.
  **The lockfile change is the larger half.** `nvidia-*` plus `triton` were **2,480 MB of the 3,179 MB** of Linux wheels, 78% of the payload, and no environment this project runs in has a GPU: CI runners are CPU, Fly.io is CPU, and `config.py` already noted fp16 is meaningless on CPU-only hosts. Pinned to the pytorch CPU index in `pyproject.toml` for **local, CI and the container alike**, not just inside the image. Doing it in the image alone would have been smaller today and would have left CI scoring the golden set on one torch build while production ran another, with nothing detecting it, which is the shape of defect that already cost this project a silent recall 0.45. `uv.lock` is in the eval's trigger paths precisely so a torch bump gets re-measured.
  **Two defects were found by running the image, and neither was visible in the file.** Model paths were first resolved into the CMD's shell, which meant anything overriding CMD saw nothing: `docker run <image> python -m octopus_ai.evaluation --shard ...` is exactly how CI's shards would invoke this, and it failed on an empty path with a repo-id error. They are now stable symlinks set as plain `ENV`, inherited by every process. And passing a developer's `services/ai/.env` straight in drags a host-specific `EMBED_LOCAL_PATH` into the container and breaks its own layout, so the image owns model **location** while the environment supplies only secrets, which is the same identity/location split ADR-0008 drew for a different reason. Also load-bearing and non-obvious: the source sits at `/app/services/ai/src` rather than `/app`, because `config.py` resolves `_REPO_ROOT` as `parents[4]` of itself and a flattened layout is an `IndexError` at import.
  Verified end to end on Docker Desktop: image builds, service reaches `configured: true`, both models load from the baked paths under `HF_HUB_OFFLINE=1`, and the reranker separates a covered query from an uncovered one at 0.9567 against 0.000017. 232 Python tests still green on the relocked CPU torch. An `ai-image` CI job builds it on any PR touching `services/ai/` and publishes to GHCR from `main`, with the layer cache in the registry rather than the Actions cache, since the weights layer alone is 4.6GB against a 10GB per-repository limit the uv and HF caches already share. The CMD-override regression is now a smoke test rather than something to remember.
  **The eval shards are deliberately left on the existing path, and that is the honest half.** Rerouting them through the image was the original motivation, since ~90s of setup per shard is the floor that stopped further splitting from helping. But most of that 90s was `uv sync` pulling the CUDA stack, which the lockfile pin has now removed from every install including CI's; what remains is restoring 4.6GB of weights from the Actions cache, and pulling an image containing those same weights moves the same bytes. That might win and might not, and asserting it without measuring would be precisely the unmeasured "obvious fix" the three-shard split already disproved once.

- **fix(workflow): the router's first rule has never been able to fire, because nothing has ever written the column it reads.** `router.ts` sends a `high_risk` task to `needs_user` whatever the plan labelled its owner. That is rules 7 and 11 applied to the router, it is the guard against a planner handing an irreversible step to the AI, and `20260813120000` says as much on the column itself. It is implemented, unit-tested, and named in three documents. **`materialise_plan` inserts seven columns and `risk_tier` is not one of them**, so every task ever built from a plan card has taken the default `reversible` and the rule has been unreachable since the day it shipped. Rule 4 lost its `read_only` exemption the same way, so every uncited AI step has been escalating to a marketplace that does not exist. Found by reading the router against the insert rather than by anything failing, which is the point: **no type check, lint, advisor or pgTAP suite asks whether a column has a writer.** Costless while the only thing an AI task can do is write prose, and not costless at all once `set_budget` and `publish_content` land.
  **The model proposes the tier and code may only raise it.** The planner is asked a per-step question it can answer by looking at the step ("if this ran now with nobody watching, what would it change outside this system?"), then `risk.py` raises it where the words commit to spending, publishing, connecting an account or committing the person to somebody, with no path that lowers one. That split is the **third** occurrence of a shape this project has already measured twice: decomposition was told "most goals need one or two stages" and took the north-star case from coverage 1.00 to 0.33, the groundedness gate was told "when unsure, answer false" and refused 0.36 of legitimate goals. A model answers a per-item question well and agrees-then-ignores a disposition.
  **The clamp errs toward over-restricting, and one pattern is narrowed against that grain rather than uniformly.** A false positive is one user touch, a false negative is unattended spending, so a match wins. But `launch` is the most common word in a marketing plan and the bare pattern clamped "Draft the launch ads" on the first test run, which would have put an approval badge on most of the creative stage and taught people to approve without reading. It now fires in verb position only. The determiner-less imperative is a **known miss, pinned by a test** rather than papered over, since the phrasings that reach the act in practice are caught by `publish` and `go live`.
  **Absent is not the same as unrecognised**, and `20260816120000` treats them differently: a card written before the field defaults to `reversible`, which is exactly what those cards already materialised as, so nothing regresses; a tier that is present and unreadable raises, mirroring the owner mapping beside it. The riskiest line turned out to be the wire mapping, where both new fields carry contract defaults, so spreading the core's snake_case step would have parsed cleanly and silently landed everything on `reversible` again. Mapped field by field, extracted as a pure function, and pinned. `acceptance_criteria` ships alongside because the marketplace's maker-checker validates node proof against it and backfilling criteria for finished work is far more expensive than emitting them with the step; its default also moves from `'{}'` to `'[]'`, since every reader wants a list. The card now shows a risk chip for `high_risk` and `external` only, word plus icon, on new `--warn` tokens rather than coral, which already means "a human does this". 232 Python tests (+24), 19 Node (+3), pgTAP `materialise_plan.sql` 19 to 25 assertions.
  **Applied and verified against the live database: 92 pgTAP assertions across four suites, zero failures**, including that an AI-owned high-risk step is stored as `high_risk`, which is the fact the router's first rule depends on and the one that was false. **And running it turned up a test defect that had been silently true for weeks.** The atomicity assertion read `count(*) from public.projects = 2`, which is a claim about the whole database rather than about anything the suite did. It passed for exactly as long as the database happened to hold no projects, and the moment real work existed it reported `have: 3, want: 2` about a row the test never touched. Now scoped to the four cards that are supposed to fail, asserting they left **nothing** behind, which is the property the comment always claimed. A test that quietly depends on the rest of the database being empty starts lying the day the product is used, and pgTAP is not in CI to catch it.

- **feat(workflow): a step waiting on the person can now be answered, which closes the loop.** The last dead end. A task reached `NEEDS_USER`, the digest said so, and there was no way to reply that moved anything: the reply was read as a brand new goal, because nothing in the room recorded which steps the question was about. The waiting digest now carries a question card holding those task ids, `decideIntakeTurn` gains a `task_answer` turn that is checked **before** the intake branches, and the answer completes the steps.

  **Their answer is the deliverable, not context.** The plan gave them work only they could do, a budget ceiling, a positioning call, which analytics source counts as the truth, so answering **is** doing the step. It is stored as an artifact `created_by: 'user'` with **no citations**, deliberately: a person's own decision rests on no retrieved source, and attaching one would attribute their judgement to the corpus. The checker never sees it, because a human answering is not a maker to be checked.

  **And the state machine had a hole this exposed.** The only arc out of `NEEDS_USER` was back to `ROUTING`, which `business-projects-workflow.md` draws as "a user who answers". Follow it: the router applies rule 2 to a `user`-owned task and sends it to `NEEDS_USER` again. **The answer had nowhere to land and the loop had no end**, silently, with the task simply waiting forever. `20260815220000` adds `NEEDS_USER → APPROVED` and the doc's diagram is updated as the specification it is, since `APPROVED` is what satisfies dependents and is therefore exactly what should let the rest of the graph move.

  Three properties carried over rather than reinvented: the card is consumed **before** the tasks are touched, so a second message racing it finds nothing to answer; completion is best effort per task, so one that will not move does not strand the others; and a non-owner still cannot answer, enforced in `decideIntakeTurn` rather than on the embed's `required_role`, because an answer arrives as a chat message and never reaches the route where that role is checked. The card is offered only for `needs_user`: an escalated task waits on an expert, and inviting an answer nobody can act on would be a false offer. 53 core tests (+3).

  **The first real answer was lost, and the way it was lost is the more useful half.** `artifact_kind` offers `draft`, `analysis`, `asset` and `proof`, all of which describe something produced FOR someone, and a person's decision is none of those, so the insert was rejected on an invalid enum value. Each task failed, each failure was logged, and the run had already consumed the question card. So the person answered, the question vanished, no step moved, and **the room said nothing at all**. The ordering that makes a race safe is exactly what made the failure silent. `20260815230000` adds the `answer` kind, and the run now **reopens the card** when nothing completes and says so plainly, because losing someone's reply is bad and losing it without telling them is worse. The lost answer was replayed against the three waiting steps rather than asking for it again.

- **feat(chat): the work the agent does is now something you can read.** With the scheduler finally able to move a task, the next gap became obvious the moment it ran: an approved AI step wrote a full artifact, a title, a body and its cited sources, into a table only a developer with SQL could reach. The person approved a plan, waited, and saw nothing. **Planning visibly and delivering invisibly is worse than doing neither, because it looks like it stopped.** `20260815210000` adds the `artifact` embed component, the executor posts one the moment a step passes review, and `ArtifactCard.tsx` renders it.

  Same two-row shape the plan uses, and for the same reason: the message body carries the work in plain text, so it survives in a notification, in the audit trail, and in any client that does not know this embed type, with the card an enhancement rather than the only way to read it. **An uncited deliverable is labelled in words**, never by colour alone, because rule 10 forbids letting one pass as grounded. **It reports rather than asks:** no approve button, since reviewing a deliverable is a real decision that belongs with the marketplace's maker-checker, and a button recording a verdict nobody considered is worse than no button at all. The state is `reported` rather than `pending` or `approved` for the same reason the question card got `answered`: `feedback_events` reads that column as a training label, so `pending` would claim somebody owes an action and `approved` would invent a human decision. One delivery per artifact, keyed on the artifact id, so a retried run reaching approval twice collides instead of posting the work again. Posting never throws: the task is approved and the artifact stored, and failing to announce it must not undo either.

  **Measured on the live database rather than asserted:** the first real project ran to **7 approved tasks, 7 artifacts, all 7 cited**, bodies between 831 and 2217 characters, with 3 waiting on the person, 4 escalated and 2 still drafting. That is the first time this system has produced delivered work end to end.

  Found while styling it: `chat.css` refers to `--hairline` and `--warning`, and **neither is defined anywhere**, so those declarations have silently done nothing. Details that took thought rather than typing. Terminal is checked first so no arc can resurrect a cancelled task. - **feat(rag): the groundedness gate, because a threshold ranks and cannot decide scope.** The one item blocking Phase 2, and it was blocking it for a reason the docs already recorded as **measured rather than suspected**: a rerank score answers "which chunk fits this query best", and that question always has an answer when the query is marketing and the entire corpus is marketing. - **fix(db): revoke default privileges that RLS cannot protect against.** Found while verifying the grants on the new `action_embeds` table: Supabase's default privileges had granted `REFERENCES, TRIGGER, TRUNCATE` to **anon** on every table in `public`, and `TRUNCATE` to `authenticated`. RLS filters rows a grant already permits, but **`TRUNCATE` is not row-level and bypasses policies entirely**, so a role holding it can empty a table whatever the policies say. `anon` held it on `messages`, `rooms` and the whole RAG corpus, flatly contradicting `20260728170000`'s "anon gets nothing. No unauthenticated surface exists in chat." Honestly scoped: **not remotely exploitable**, since PostgREST exposes no `TRUNCATE` verb, so there was no route to it through the API; closed because a privilege that cannot be justified should not be held. `anon` now has nothing at all and `authenticated` has exactly `SELECT` (plus `INSERT` on messages, `UPDATE` on profiles), verified against the live database. The durable half is an `alter default privileges`, without which the cleanup decays the next time anyone adds a table.

- **fix(ai): a rate limit is not a transient 5xx.** The first armed CI eval run failed, and the log showed why twice over. `_post_with_retry` treated `429` exactly like a `503`, retrying after 0.5s and 1.0s; a provider quota is quoted **per minute**, so those retries cannot succeed and each one spends another call against the same exhausted quota, making failure certain rather than recovering from it. `429` now backs off on a minute scale (`Retry-After` when the provider sends one, else a 20s floor), while 5xx keeps its fast curve so a blip does not become a timeout inside the agent step. The floor is deliberately not a full minute: this runs inside a bounded agent step, and waiting out the whole window trades a fast failure for a slow one. Separately, CI's eval pacing went from 7s (≈8.5 calls/min, close enough to the 10/min trial cap that it tripped partway through the set) to 10s. 59 Python tests (6 new), sleeps captured rather than performed so the suite asserts the schedule without waiting for it. **The real fix remains a production Cohere key**, which the same cap will otherwise impose on live traffic.

- **feat(rag): retrieval eval gate on a versioned golden set.** `services/ai/eval/golden.json` (14 cases) plus `python -m octopus_ai.evaluation`, which runs the real pipeline and exits non-zero on a regression. A miss makes the agent refuse an answerable question, which is unhelpful but safe; a leak hands the planner loosely-related text that it then grounds a confident cited answer in, so one leak fails the run. - **feat(rag): local BGE-M3 embeddings, selectable per environment** ([ADR-0008](docs/40-adr/0008-local-bge-m3-embeddings.md)). `EMBED_PROVIDER=local` runs `BAAI/bge-m3` in-process via FlagEmbedding instead of calling OpenAI, so no corpus text leaves the machine.
